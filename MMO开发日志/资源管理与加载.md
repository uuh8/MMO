## Q&A

### 1. 你的项目是如何做资源管理的？有什么不足？

目前项目使用 **Resources** 文件夹 + **Resloader** 封装的方案。优点是开发简单，**路径字符串直接加载**；缺点有三：

1. 第一，**Resources** 下所有资源都会打进包体，包括废弃文件，无法按需分包；
2. 第二，**Resources.Load 是同步阻塞调用，大资源加载时会卡帧**，我在 SoundManager 里加了 **Dictionary** 缓存来缓解重复加载问题；
3. 第三，Resources 内容打包后无法热更新。

场景加载用的是 **LoadSceneAsync** 异步方案，不阻塞主线程，通过协程每帧轮询 progress 可以驱动 Loading 进度条。如果要做得更好，应该迁移到 Addressables，它支持异步加载、资源引用计数管理和热更新分包，是目前手游项目的标准方案。

### 2. 你游戏中的资源是如何管理的？你是如何实现各类资源的加载的？

我项目目前用的是 Unity 的 **Resources 文件夹方案**，所有资源按类型分目录放在 **Resources** 下，通过统一的 **Resloader** 入口加载。选这个方案主要是因为开发阶段简单直接，**路径字符串就能拿到资源**，不需要额外配置。

但这个方案有几个明显的问题我是清楚的。

1. 第一是它是**同步加载，在主线程执行，资源大的时候会卡帧**。我在音频这块做了改进，加了一层 Dictionary 缓存，第一次加载后就常驻内存，后续播放直接命中缓存，避免重复 IO。场景加载我用的是 `LoadSceneAsync` 异步方案，不阻塞主线程，通过协程每帧推进。
2. 第二个问题是 **Resources 下的所有文件打包时会全部打进包体，包括废弃资源，包体控制很差**。
3. 第三是**没有热更新能力**，资源打进包就固定了。

如果要做得更完善，应该迁移到 **Addressables**。它解决了这三个问题：

1. 异步加载**不卡主线程**，按需分包控制包体大小；
2. 同时支持从远程 CDN 下载资源实现热更新；
3. 它还有引用计数机制，能精确控制资源的生命周期，知道什么时候该卸载，不像 Resources 需要手动管理。

### 1. Resloader.cs — 资源加载层

```csharp
class Resloader
{
    public static T Load<T>(string path) where T : UnityEngine.Object
    {
        return Resources.Load<T>(path); // 同步阻塞加载
    }
}
```

**它是什么**：对 `Resources.Load` 的薄封装，统一了加载入口。

**Resources 文件夹的工作原理**：

- 放在 `Resources/` 下的文件在打包时会被**全部打进包体**，无论有没有被引用
- 运行时通过 **路径字符串** 加载，Unity 维护一张路径→资源的索引表
- 加载是**同步的**，在主线程执行，文件大时会卡帧

**根本缺陷**（面试必说）：

1. **包体膨胀**：**Resources** 下所有文件都被打包，包括废弃资源
2. **无法热更新**：**Resources** 文件夹内容在打包后不可替换
3. **同步 IO**：**`Resources.Load` 阻塞主线程**
4. **内存不可控**：加载进来的资源没有自动卸载机制，需要手动 `Resources.UnloadAsset`
