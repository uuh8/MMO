## 遇到的问题

### 1. 我在本地用 **两个客户端同时进入同一张地图** 做联调测试。现象很诡异：A 先进入时一切正常，但 B 进入后出现了“灵魂互换”——A 的视角和操作变成了 B，B 反过来也变成 A；更离谱的是，A 的视角里还像是能同时操控 A 和 B 两个角色。

排查时我把链路拆成三段：

1. **进入游戏请求/响应（`UserGameEnterRequest` / `UserGameEnterResponse`）**：确认“账号选择的角色是谁”。
2. **进入地图广播（`MapCharacterEnterResponse`）**：确认“地图里有哪些可见实体”和“客户端如何决定本地玩家”。
3. **移动同步（`MapEntitySyncRequest`/`Response`）**：确认同步 id 使用的是 `entity_id` 还是 `db id`、服务端是否按 `Session` 做权威校验。

核心策略是：**先检查“身份绑定”和“对象标识”，再看同步算法**。因为只要“我是谁”错了，再正确的同步都会表现成错乱。

#### 根因总结

第一，`MapCharacterEnterResponse` 在服务端有两种发送方式：

- 给新进入地图者发**“全量列表”**（地图内所有玩家/怪物）。
- 给已在地图的玩家发**“增量列表”**（只包含新进来的那一个角色）。

客户端原逻辑在处理 `MapCharacterEnterResponse` 时直接拿 `response.Characters[0]` 当作自己并覆盖 `CurrentCharacter`，于是当第二个人进入时，老玩家收到的增量包里 `[0]` 当然就是“对方”，从而 **把自己误认成对方**，导致视角/输入/同步主体全部串号。

第二，同一个协议在客户端被多个 Service（如 `UserService`/`MapService`）重复处理，且其中一处还存在“`CurrentCharacter==null` 就随便认一个 Player”的逻辑。这会造成 **状态被重复覆盖**，顺序不同就产生竞态，进一步放大问题。

#### 解决方案与落地改动

解决思路**是把“身份确认”和“地图实体列表处理”彻底拆开**，并消灭对“数组顺序”的依赖。

1. **在 `UserGameEnterResponse` 阶段确定本地角色**
    `OnGameEnter` 只负责一次性地把 `CurrentCharacter = response.Character`（这是服务端明确返回的“我是谁”，db id 稳定），并完成背包/装备/任务/好友等初始化。之后任何地图广播都不允许覆盖这个身份引用。
2. **修改 `OnCharacterEnterMap`：不再用 `Characters[0]`，改为按 dbId 匹配自己**
    处理 `MapCharacterEnterResponse` 时，先用 `CurrentCharacter.Id`（db id）在 `response.Characters` 里查找“我自己那条”。

- 找不到：说明这是别人进入地图的增量包，只创建/更新对方实体，不加载场景、不改 `CurrentCharacter`。
- 找到：说明是我自己进图的全量包，只同步地图相关字段（entity_id、位置等），然后加载场景并把可见列表交给实体管理器生成。

1. **调整 `MapService`：不再负责 `LoadScene`/不再猜测 `CurrentCharacter`**
    `MapService` 专注维护**地图实体**（`CharacterManager`/`EntityManager`），不再做 `EnterMap`，也不再改 `CurrentCharacter`，避免与 `UserService` 重复处理同一条消息导致竞态。

## Q&A

### 1. “进入游戏”的这个过程是什么样的？进入游戏后的“移动同步”怎么实现？

#### 进入游戏的过程是什么样的

进入游戏我把它拆成两阶段：**身份确认**和**进入地图**。客户端在角色选择界面点击“进入游戏”后，会向服务端发送 `UserGameEnterRequest`，其中携带选中的 **角色 dbId**（`Character` 表主键）。服务端收到后，会先校验这个 `dbId` 是否属于当前登录账号，然后把数据库持久化对象 `TCharacter` 转成运行时实体 `Character`（包括基础属性、背包/装备/任务/好友等管理器初始化），并把 `Session.Character` 绑定到这个运行时角色，确保后续所有请求都能从 `Session` 定位到“这条连接到底在操作哪个角色”。接着服务端回 `UserGameEnterResponse`，把该角色的 `NCharacterInfo` 下发给客户端，客户端用它一次性确定 `CurrentCharacter`（身份锚点）并初始化背包/装备/任务/好友等本地管理器。

身份确认完成后，服务端会把该角色放进目标地图（`Map.CharacterEnter`），构造并发送 `MapCharacterEnterResponse`。这条消息的语义是“地图可见实体列表”：对**新进入者**发送全量列表（自己 + 地图已有玩家 + 怪物等），对**地图内其他玩家**发送增量列表（只包含新进入者）。客户端收到后会加载对应场景，并在本地生成/刷新地图实体对象，但这里不会再改变“我是谁”，只会根据 `dbId` 匹配到自己的那条记录，补齐 `entity_id`、位置等地图相关信息。

#### 进入游戏后的移动同步怎么实现

移动同步采用“**服务器权威 + 客户端上报 + 服务器广播**”的模式。客户端每帧或按固定频率向服务端发送 `MapEntitySyncRequest`，内容是 `NEntitySync`（包含实体 id、事件类型、位置/朝向/速度等）。这里的实体定位使用 **`entity_id`**（运行时实体实例 id），而不是 `dbId`；`dbId` 只用于身份/存档，`entity_id` 用于地图内同步路由。

服务端收到移动同步请求后，会先通过 `Session.Character` 做权威校验：这条连接只能更新自己控制的角色实体（通常校验 `entitySync.id == Session.Character.entityId`），通过才更新服务端的权威位置状态，然后把这条 `NEntitySync` 广播给同地图内的其他玩家（发送 `MapEntitySyncResponse`，里面是一个或多个 `entitySync`）。客户端收到广播后，只更新“远端实体”的显示状态，通常会做插值/缓动来消除网络抖动；本地玩家可以做轻量预测，但最终以服务端回包/广播为准，避免作弊和状态漂移。

### 2. 帧同步的“input”是弱信任的，逻辑结果必须由逻辑计算决定，那么这个逻辑计算是在客户端进行的还是服务端？如果是在服务端，这不是有悖于“服务端只做转发工作”的初衷吗？如果是在客户端，这个逻辑运算是在`FrameInput`构造完成之前还是完成之后？

先说最纯粹、最原教旨主义的帧同步：

- 服务器只干一件事：**收集所有客户端输入、按帧号广播**。
   它不做任何游戏逻辑计算。
- 所有客户端**在收到完整输入帧后，本地执行逻辑帧计算**。
- 逻辑帧计算包括移动、攻击、伤害判定、子弹飞行、状态变化……全部。
- 只要逻辑代码完全一致、输入数据一致、随机种子一致——所有人世界一致。

这就是《星际争霸》《红警》《魔兽争霸III》的模式。
核心思想是：**世界的真相是所有客户端“独立计算后得出的相同结果”**，服务器只是一个同步器（Lockstep Synchronizer）。

> **因此在理想帧同步下，逻辑计算一定在客户端，不在服务端**。
> 服务器如果干预计算，反而破坏“确定性”。



------

### 3. 作弊与恶意输入怎么办？

你提到的疑问正是这里产生的：

> 如果逻辑都在客户端，那客户端不是可以乱算吗？

对，单纯的帧同步无法防止修改逻辑或输入——这就是为什么**“input 是弱信任”**，但又**必须验证**。

所以实际工程里，出现了三种常见**变体架构**：

**① 纯帧同步（经典 Lockstep）**

- 服务器：只转发输入。
- 客户端：独立执行完整逻辑。
- 优点：延迟可预测、计算分布式。
- 缺点：完全信任客户端，易被修改。

代表作：星际争霸、魔兽争霸、Dota 1。

**② 半权威帧同步（Authoritative Lockstep / 验证式帧同步）**

- 服务器：转发输入 + 逻辑验证 + 随机抽查复算。
- 客户端：执行完整逻辑。
- 验证点：
  - **服务器**不参与每帧模拟，但**能检测“输入是否合法”**（技能是否冷却、距离是否够等）。
  - 定期选取关键帧复算，对比哈希验证确定性。
- 如果发现偏差，服务器发“状态修正帧”或踢出异常客户端。

代表作：《王者荣耀》《LOL》《阴阳师百闻牌》。

这种架构就是主流手游/竞技网游用的模式：

> 客户端负责逻辑，服务器只复查关键帧或过滤非法输入。

所以说**服务器“仍然只做转发”，但加了轻量的“验证层”**，并非全盘计算。

**③ 混合同步（Hybrid Sync）**

- **小范围使用帧同步**（例如局部战斗逻辑），
- **大范围使用状态同步**（例如世界位置、场景加载）。
- 服务器既有权威数据，又允许客户端进行局部逻辑预测。

代表作：PUBG、《Apex Legends》。

在这些游戏中，**输入还是客户端产生的**，但：

- 服务器会**定期下发“真相帧”**（snapshot）。
- 客户端发现自己模拟与真相不符 → **回滚**重演（rollback）。

------

让我们具体看一帧内的流程。以典型帧同步引擎为例（王者荣耀式）：

```
客户端逻辑帧 F 流程：

1. 玩家按键输入 → 封装 InputCommand
2. FrameInput = { playerId, commandType, param }
3. 发给服务器
4. 服务器收集各玩家 FrameInput → 构成 FramePacket(F)
5. 广播 FramePacket(F) 给所有客户端
6. 客户端收到 FramePacket(F)
7. 执行逻辑计算 (SimulateFrame(F, allInputs))
8. 输出新状态，渲染
```

可见：

- **FrameInput 构造阶段**只是**记录意图**（例如“按下技能1”），不包含逻辑结果。
- **逻辑计算阶段**（例如“技能1 造成 100 点伤害”）在收到完整的 `FramePacket` 后执行。
- 所以逻辑计算在 **FrameInput 之后**，在帧执行阶段。

也就是说：

> “FrameInput” 只是“输入意图快照”；真正的逻辑计算一定发生在**“帧执行阶段”**，而**不是构造阶段**。



### 4. MMO 为什么不用帧同步？

帧同步有个致命要求：**逻辑必须确定性（deterministic）**。同一帧、同一输入，任何平台、CPU、浮点差异都必须得出同样结果。

MMO 不采用帧同步，根本原因在于其**世界规模、交互复杂性与延迟容忍度**都与帧同步的设计假设相冲突。帧同步是一种**“所有客户端以相同帧号执行完全相同逻辑”**的机制，要求逻辑确定性和帧节奏一致；而 MMO 的系统设计从一开始就建立在**大规模并发、异步事件驱动、服务器权威**的基础上，这使帧同步在 MMO 场景下几乎不可行。

首先，**MMO 的世界规模过大**。帧同步要求所有参与者在**同一个逻辑时钟**上前进，这在一个拥有成千上万玩家的开放世界中是不可能的。**MMO 的每个玩家所见的世界都只是全局状态的一个局部子集**，服务器通过“兴趣管理（Area of Interest）”和“地图分区（Scene Partitioning）”让玩家仅与附近对象交互。要让全世界在一条统一的逻辑帧线上同步，通信量会呈指数级膨胀，延迟积累后根本无法维持实时。

其次，**MMO 的交互是异步的，而帧同步要求完全同步**。在帧同步中，**服务器必须等待所有客户端输入齐全**才能推进下一逻辑帧，这意味着任意一个玩家网络波动都可能让全局卡顿。而 MMO 中大量行为（聊天、交易、任务触发、AI 刷新、Buff 持续等）都是异步事件，彼此之间**无需帧级一致性**。用帧同步去强行统一这些节奏，会让整个系统性能崩溃。

第三，**MMO 对确定性逻辑的要求与其系统复杂度不兼容**。帧同步要求逻辑完全确定：**同样输入在任何机器上必须得出完全相同结果**。这要求**禁用浮点误差**、**随机性**、甚至**平台差异**。而 MMO 的逻辑往往涉及大量**数据库交互**、**装备属性计算**、**概率事件**、**AI 行为树**等，这些都无法保证完全确定性。要让这些复杂逻辑满足帧同步的严格 determinism 几乎是工程上不可承受的代价。

第四，**延迟和公平性的需求完全不同**。帧同步存在**“慢者拖全局”**的问题，一个玩家高延迟就会阻塞所有人，因此只适合小规模、高实时性的对局（如 MOBA 或 RTS）。而 MMO 的延迟容忍度很高——只要角色动作在 100~300 毫秒内响应即可被玩家接受。与其让全球玩家等最慢那一帧，不如让服务器异步更新状态、客户端插值显示，这样体验更流畅。

最后，**权威性和安全性决定了 MMO 必须由服务器计算逻辑**。在帧同步中，逻辑计算在客户端进行，服务器只负责帧广播，这意味着一旦客户端被篡改，作弊输入会影响所有人。而 MMO 涉及经济系统、掉落系统、经验值与货币，这些都必须由服务器掌握最终结果，否则游戏世界的可信度就会崩塌。因此 MMO 必然采用状态同步，由**服务器维护“世界真相”**，客户端仅作表现。

综上，MMO 不采用帧同步，不是因为帧同步不够先进，而是因为它的**“确定性与同步性假设”**在大规模分布式世界中完全不成立。帧同步擅长的是**公平的实时小局对战**，而 MMO 追求的是**大世界的稳定**、可扩展与安全，这两者在设计哲学上天然背离。



### 5. 帧同步存在**“慢者拖全局”**的问题，一个玩家高延迟就会阻塞所有人，但是玩LOL的时候，其他玩家的延迟和我本地的延迟没关系，有时其他玩家延迟高，但是我的延迟依然低，这是什么原因？

**LOL 并不是纯粹的帧同步**，而是一种经过深度改造的“**半权威帧同步（Authoritative Lockstep）**”或称“**延迟容忍型帧同步**”架构。也就是说，LOL 在逻辑层面依然用帧驱动思想来保证公平与重现性，但它通过**局部预测 + 服务器裁决 + 动画延迟补偿**等机制，彻底解决了传统帧同步中“所有人等最慢者”的问题。

------

从技术上讲，**LOL 的逻辑帧由服务器驱动，而不是由客户端互相等待**。在经典帧同步（如《星际争霸》）中，服务器在每一逻辑帧都必须等待所有玩家输入到齐，然后再推进帧号；而 LOL 改成了**服务器拥有帧时钟**，只等待一个最大延迟阈值（例如 100ms）后，无论输入是否齐全都推进下一帧。没有按时到的客户端输入会被判为“空输入”或使用上一次的状态，这样服务器的逻辑时钟始终稳定前进。于是，一个延迟 200ms 的玩家只是“在别人眼中动作更迟发出”，而不会阻塞别人的帧推进。

------

同时，**客户端的画面是预测+回滚机制下的“伪同步”**。当你点击移动或释放技能时，本地客户端会立刻在画面上播放动画**（预测执行）**，不需要等服务器帧返回。服务器稍后下发该帧的真实结算结果（命中、伤害、位移等），如果与预测一致，就继续播放；如果不一致，客户端会进行一次**“无感回滚”**或**位置矫正**。这种局部预测让你感觉“操作立即生效”，但逻辑真相仍然由服务器维护。也就是说，**LOL 的帧同步是逻辑上的，而非物理帧锁定的**。

------

再者，LOL 的网络架构是**客户端-服务器一对多单播（unicast）结构**，而不是**早期 LAN 游戏的“全网广播帧同步”**。每个玩家只与服务器通信，不与其他玩家直连。服务器将所有玩家的输入收集并转发到各自客户端，但延迟计算是**每人独立的 RTT（往返时间）**。因此，别人的延迟不会直接影响你的网络往返——你只受自己与服务器之间的链路影响。这一点与“P2P式帧同步”完全不同。

------

最后，**LOL 的引擎在表现层做了大量延迟补偿**。例如普攻动画、技能命中、粒子播放、击退效果等都经过时间轴调整，使高延迟玩家看到的画面在**逻辑上延后一点**，但视觉上仍然连贯；而低延迟玩家则几乎实时看到结果。这种“视觉时间轴偏移”隐藏了逻辑帧延迟，让各玩家都感觉流畅。

------

总结来说，《英雄联盟》确实继承了帧同步的“帧号一致”“逻辑确定性”等思想，但通过三个关键改变摆脱了“慢者拖全局”的缺陷：

1. **逻辑帧由服务器统一推进，不等所有人输入。**
2. **客户端使用 “预测与回滚” 机制保证操作即时性。**
3. **通信是 “点对服务器” 的单播模式，延迟独立。**

因此，当别的玩家网络糟糕时，服务器会让他们“掉帧”或“回滚”自己的状态，而不会让整场游戏停摆。换句话说，LOL 并不是“经典帧同步”，而是**在帧同步理念上构建的混合同步系统**，兼顾了公平性与流畅性——既保留帧一致逻辑，又避免全局锁步延迟。

### 6. 客户端和实体相关的脚本文件：`Entity` 、`EntityManager`、`EntityController`的作用是什么？对于同步有什么作用？

核心认知：**客户端的 Entity 是“同步与预测的最小逻辑单元”，EntityController 是“逻辑→可视/动画的适配器”，EntityManager 是“全局注册表与销毁通知器”。**

#### **1. `Entity`（逻辑镜像）——状态的最小单元**

 `Entity` 是逻辑层的纯数据载体：它保存 `entityId`、逻辑坐标 `position`/`direction`/`speed`，并且暴露一个 `EntityData`（`NEntity`）接口：当网络层把权威快照赋给 `Entity.EntityData` 时，会通过 `SetEntityData()` 把协议数据“落地”成逻辑字段；反过来，`OnUpdate(delta)` 会按速度/方向做离散积分并把结果回写到 `entityData`（方便发包）。也就是说，`Entity` 是“要同步的字段 + 本地逻辑推进”的组合，是客户端与服务器对话的最小语义单元。 

#### **2. `EntityController`（表现/适配器）——把逻辑映射到画面**

 `EntityController` 绑在每个角色的 `GameObject` 上，负责把 **`Entity` 的逻辑值**映射为 **Unity 世界坐标**并驱动 `Rigidbody`/`Animator`。它在 `Start()` 时用 `EntityManager.RegisterEntityChangeNotify` 注册一个**通知接收者**（用于实体删除回调），在 `FixedUpdate()` 里无论是不是本地玩家都会先 `entity.OnUpdate()`（推进逻辑），但**仅在非本地玩家时**才把逻辑投影到可视层（`UpdateTransform()` 用 `rb.MovePosition` 与 `transform.forward`），而本地玩家的可视运动由 `PlayerInputController` 驱动以保证手感（因此 `EntityController` 避免覆盖本地刚体）。`OnEntityEvent` 则把事件（Move/Idle/Jump）映射到 Animator。

#### **3. `EntityManager`（注册中心 / 生命周期管理）**

 `EntityManager` 是客户端对所有 `Entity` 的**集中注册表**：它维护 `Dictionary<int, Entity> entities` 作为**本地所有实体的索引**，并维护一个 **`notifiers` 字典把实体 id 映射到实现 `IEntityNotify` 的接收者**（通常是对应实体的 `EntityController`）。当网络层或上层管理器创建或删除一个实体时，它会调用 `AddEntity(entity)` / `RemoveEntity(nentity)` 来更新字典；`RemoveEntity` 同时会查 `notifiers` 并调用 `OnEntityRemoved()`，从而驱动 `EntityController` 销毁对应 `GameObject`（解耦了“数据 → 视图”的生命周期）。换句话说，`EntityManager` 是**查表 / 事件路由 / 生命周期协调**的单点。 

#### **4. 典型的同步实现流程（端到端）**

- 服务端按 tick（权威）模拟 `Entity`，产生 `NEntity` 快照并通过消息发出；
- 客户端网络层收到 `NEntity`：若是新实体，构造 `Entity` 并 `EntityManager.AddEntity(entity)`；若已存在，直接把 `Entity.EntityData = receivedNEntity`（触发 `SetEntityData` → 更新逻辑字段）。这一步实现**“把快照写进本地镜像”**。
- 一旦本地 `Entity` 更新，绑定到该实体的 `EntityController`（已在 `Start()` 中注册过 `EntityManager`）会在后续的 `FixedUpdate()` / `Update()` 周期里把**逻辑值映射到可视层**（远端实体走 `UpdateTransform()`、本地实体由输入控制器驱动并回写逻辑）。这样客户端完成从**“权威快照 → 逻辑镜像 → 视觉表现”**的完整链路（`Entity` 作状态载体，`EntityController` 做适配，`EntityManager` 做注册与事件路由）。

#### **5. `EntityManager` 的更深层价值（为什么要集中管理）**

- **快速查找**：任何系统（UI、小地图、AOI 管理器）只需要 `EntityManager` 就能通过 id 找到实体数据或决定是否需要显示；
- **统一生命周期事件**：当服务端删除实体时，不需要每个 `controller` 去轮询消息；网络层只调用 `EntityManager.RemoveEntity`，由它统一通知对应 `EntityController` 去清理（见 `OnEntityRemoved`），避免内存泄漏或孤立 `GameObject`；
- **职责分离**：把**“谁存实体、谁通知、谁驱动视图”**分开，便于替换（比如把本地字典换成更复杂的分区索引、加 LRU 回收、做对象池）；

#### **6. 同步思路（差量/全量、插值/外推、预测/校正）如何映射到这三份脚本**

- **全量快照**：服务器每 tick 发送完整 `NEntity`→ 客户端 `Entity.EntityData = NEntity` 全量覆盖（简单但带宽大）。`Entity` 的 `SetEntityData` 就完成落地。
- **差量/事件**：服务器只在状态改变时发送事件（如速度/动画切换），客户端把这些事件应用到 `Entity` 或直接调用 `EntityController.OnEntityEvent` 播动画，节省带宽。`EntityController.OnEntityEvent` 接受事件并切动画就是为这类差量设计的。
- **插值 vs 外推**：收到两个时间点的快照后，客户端可以在渲染帧内对 `Entity.position` 做插值（平滑移动远端玩家）；目前 `EntityController.UpdateTransform()` 直接 `rb.MovePosition(this.position)`，你可以在这一步加插值缓冲逻辑（将 `lastPosition`→`targetPosition` 做 LERP），减少跳跃。
- **本地预测与服务器校正**：本地玩家先用输入驱动刚体即时移动（`PlayerInputController` 路径），并把输入序号发送给服务器；服务器回包的 `NEntity`（权威）写回 `Entity`，客户端对比并在 `LateUpdate` / 专门的 reconciliation 模块做回放与平滑修正（你的 `PlayerInputController` 就实现了一个简易的回写阈值逻辑）。`Entity` 在此扮演“预测结果与权威结果的对齐缓冲器”。

#### **一句话总结**：

- `Entity` 是**“状态载体与本地逻辑推进”的镜像**；
- `EntityController` 是**“把镜像变成画面”的适配器**；
- `EntityManager` 是“**实体注册表与事件路由器（生命周期管理器）”**。
- 三者合起来实现客户端的同步架构：网络写入 `Entity.EntityData` → `Entity` 更新逻辑字段 → `EntityController` 把逻辑映射到视觉 → `EntityManager` 管理实体表与通知销毁/查询。把 `EntityManager` 当作客户端实体的**单一真相索引与事件枢纽**来使用，会让同步实现既清晰又可扩展。

### 7. Entity和GameObject之间是什么关系？EntityManager维护了一个Dictionary<int, Entity> entities用于管理实体，而游戏中很多东西都是Entity，比如角色、怪物等等，这样Entity岂不是和GameObject的工作重复了吗？

`Entity` 是**逻辑/网络层面的状态载体**（可跨端复用、可序列化、可在服务器上运行的“真值”）；**`GameObject`** 是**表现层/渲染层面的实体实例**（包含模型、动画器、碰撞体、脚本、摄像机绑定等）。两者并不重复——而是分工：**`Entity`** 负责“我是谁/我在哪/我怎么动/我要同步什么”，**`GameObject`** 负责“我长什么样/我如何渲染/如何响应输入和物理”。把两者分离可以让服务器仅存在 `Entity`（无渲染），客户端复用同一 `Entity` 语义同时映射为视觉对象。

#### 为什么要两套东西（设计动机）

1. **跨端可复用与确定性**：服务器没有 Unity 引擎，需要纯数据的 `Entity` 去做**确定性模拟**与**带序号的快照广播**；若把逻辑耦合在 `GameObject/Transform` 上，服务器无法复用这些逻辑。
2. **解耦性能与数量级问题**：世界里可能存在成千上万的实体（AI、怪物、子弹），但只有少量需要在某个客户端被渲染。把**逻辑状态存在内存中的 `Entity`（轻量）而不是立刻实例化重型 `GameObject`**，可以做到**按需渲染**（AOI / LOD / 懒创建）。

#### 典型的生命周期与交互流程（端到端）

1. **接到网络快照或本地生成**：网络层收到 `NEntity`，创建或更新本地 `Entity`，并把它 `EntityManager.AddEntity(entity)` 注册到字典里（`entities[id] = entity`）。
2. **决定是否创建 GameObject**：`GameObjectManager`（或 `EntityManager` 的监听器）订阅实体新增事件：若该实体位于当前 AOI / 需要渲染，`GameObjectManager` 用 `Resloader` 加载 prefab 并 `Instantiate` 出 `GameObject`，然后把 `Entity` 赋给 `EntityController` / `PlayerInputController` 等组件。
3. **运行时协同**：每帧/每个 `FixedUpdate`：
   - `Entity.OnUpdate(delta)` 做逻辑积分（position/direction/speed）。
   - 若本地玩家：`PlayerInputController` 驱动 `Rigidbody` 并回写 `Entity`（预测）；
   - 若远端玩家：`EntityController` 将 `Entity` 的逻辑位置插值/映射到 `GameObject`（表现）。
4. **销毁/回收**：当实体离开 AOI 或被删除，`EntityManager.RemoveEntity(id)` 触发通知，`GameObjectManager` 接到通知后 `Destroy`（或回收到对象池）对应 `GameObject`，但 `Entity`（逻辑）可视策略依然保留或也释放，取决业务。

#### `EntityManager` 的存在意义

`EntityManager` 并不是单纯重复 `GameObject` 的字典，它是**客户端整个实体数据层的真相索引**：

- 快速查找（id → Entity），供 UI、小地图、AI、技能系统读写；
- 统一管理生命周期（Add/Remove）并广播事件（EntityAdded/Removed/Updated），让 `GameObjectManager`、UI 管理器等只需订阅事件就能创建/销毁/更新视图；
- 换言之：`EntityManager` 管的是“**逻辑对象集合与其元信息**”；`GameObjectManager` 管的是“**哪些逻辑对象需要视觉化以及视觉化如何做**”。它们合作而非重复。
