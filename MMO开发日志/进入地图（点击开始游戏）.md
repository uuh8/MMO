## 流程

### 点击“开始游戏”按钮

#### 客户端发送

客户端`UICharSelect.cs`中`OnClickPlay`方法绑定到按钮中。该方法会调用UserService中的SendGameEnter函数，随包带上所选角色索引发送UserGameEnterRequest请求到服务端。

#### 服务端处理

1. 服务端的UserService会订阅该请求，并定义了响应函数OnGameEnter，OnGameEnter中首先会通过会话信息获取当前登录用户对应的`TUser`、`TPlayer`以及角色列表，然后根据客户端传递的**角色索引**安全地检索出玩家所选的`TCharacter`对象，服务器通过`CharacterManager`的`AddCharacter`方法，将该数据库存档实体（`TCharacter`）的数据拷贝到一个新的运行时角色对象（`Character`），并将其注册到全局角色管理器内，确保运行时逻辑与数据库持久化层完全解耦。

2. 接着，服务器构造`UserGameEnterResponse`等DTO通过网络发送回客户端。`UserGameEnterResponse`中只有一个`Result`和一个`errormsg`，具体和角色进入地图相关的逻辑在下一栏`MapManager`的`CharacterEnter`方法中。

3. 最后调用MapManager中的CharacterEnter方法执行“角色进入地图”的逻辑，把**运行时角色**丢进对应地图，开始广播出生、同步周边实体等。

------

### 进入地图

#### 服务端

```c#
MapManager.Instance[dbchar.MapID].CharacterEnter(sender, character);
```

`MapManager` 的作用是负责把所有地图实例索引并管理起来，首先会**定位到对应的 `Map` 实例并进入该地图的 `CharacterEnter` 流程**（地图注册与索引由 `MapManager.Init()` 在`GameServer`**启动时就会运行**并保存到内部字典中）。

在 `Map.CharacterEnter` 内部，第一步是把运行时角色对象的地图 ID 设为当前地图的 ID，以确保后续任何基于 `character.Info.mapId` 的逻辑（例如区域查询、保存位置等）都看到最新值；接着构造一个 `MapCharacterEnterResponse` 的网络包，把当前角色的 `NCharacterInfo`（即 `character.Info`，包含 id、名字、等级、位置等关键字段）加入到响应的角色列表中，作为“自己进入地图”的信息发给自己客户端，同时把当前地图上已存在的每一个角色的信息也塞入该响应，以便让新入场的客户端一次性拿到当前 AOI 内的初始快照（代码就是把 `this.MapCharacters` 中每个 `kv.Value.character.Info` 添加到 `message.Response.mapCharacterEnter.Characters` 中）；与此同时，服务器会向每个已在地图里的连接调用 `SendCharacterEnterMap(kv.Value.connection, character.Info)`，单独发一个“有人进入地图”的通知给他们，让他们能在本地创建或更新对方的实体表现。

完成广播准备后，服务器把新角色以 `MapCharacter(conn, character)` 的形式**登记**到 `MapCharacters` 字典中（以角色 Id 为键），确保地图状态机持有该运行时对象的引用并成为后续广播、碰撞检测与更新循环的一员；最后把构造好的包含自我与周边初始实体快照的 `NetMessage` 打包并通过 `conn.SendData` 直接发回给自己客户端，让客户端开始本地镜像构建、角色渲染与本地预测逻辑。

由此可见，该方法既完成了**服务器端的注册（把运行时角色纳入地图管理）也完成了双向的网络同步：向周围玩家广播“某人进场”并向新玩家下发周边初始快照**，从而把运行时状态、AOI 注册、网络通知这三件事在一个原子化流程中串联起来。

> 需要注意的工程细节包括：保证对 `MapCharacters` 字典的并发访问安全与异常路线（进图失败时要回滚注册与释放已获取的锁）、避免在广播过程中触发延迟的数据库访问（运行时对象不应持有可触发延迟加载的 EF 实体）、对大规模地图用差分/分包策略发送 AOI 初始数据以控制带宽，以及在入场前后分别触发心跳/保存调度（例如入场后注册定期写回、断线移除时持久化位置），这些都是让 `CharacterEnter` 在负载高、并发多的线上环境稳定运行所必须考虑的实现细节。

#### 客户端

1. 客户端拿到 `MapCharacterEnterResponse` 之后，这个回调就把“服务端让你进哪个地图、你是谁”的关键信息落地，并驱动场景切换。第一步是**记录可观测性**：用日志打点 `mapId`，便于追踪一次进图链路（从点击按钮到加载完成的全程耗时）。紧接着从 `response.Characters` 里取出索引 `0` 的 `NCharacterInfo`，按你的协议约定这里就是“自己”的镜像数据（id、名字、等级、职业、出生点等）。代码把它存进 `User.Instance.CurrentCharacter`，等于把“当前操控角色”的权威快照缓存到本地用户状态，后续 UI、出生点放置、战斗面板、背包栏等都从这里取初始值。

2. 第二步是**解析目标地图并切换场景**。客户端根据 `response.mapId` 去 `DataManager.Instance.Maps[mapId].Resource` 查出要加载的 Unity 场景资源名，然后调用你自封装的 `SceneManager.Instance.LoadScene(...)`。这个 `SceneManager` 是一个 `MonoSingleton` 包装：**内部用协程启动 `UnityEngine.SceneManagement.SceneManager.LoadSceneAsync(name)` 做异步加载**，设置 `allowSceneActivation = true` 以允许在资源加载到位后自动激活场景，并把 `completed` 事件挂到 `LevelLoadCompleted`。协程里每帧轮询 `async.isDone` 并把 `async.progress` 通过 `onProgress` 回调抛给 UI（如果你绑定了进度条），加载完成后 `completed` 回调会把进度置到 1.0 并再打一条“加载完成”的日志。这段封装的意义是**把主线程阻塞的同步切换变成可控的异步切换**：你可以在加载期间展示 loading 界面、禁用交互、防抖“重复进图”的输入。

3. 第三步是**建构本地世界镜像**（这部分通常在场景加载完成后触发的初始化脚本里进行）。有了 `User.Instance.CurrentCharacter`，你的场景初始化脚本就能：1）实例化本地主角（根据 `CurrentCharacter.Class/Tid` 选择预制体，用 `CurrentCharacter` 的出生点/朝向摆放）；2）初始化相机跟随、输入组件、状态条等本地子系统；3）对“周边玩家/NPC”的初始快照进行生成（如果服务端把其他角色也随回包下发，这里遍历 `response.Characters` 的其余元素建立它们的镜像；如果没有，则等待随后的 AOI 推送/增量同步消息再逐步生成）。这一阶段建议把“自己”和“别人”走两条代码路径：自己用带控制与相机的本地预制体，别人用轻量的远端实体预制体，并把网络可写属性（位置、朝向、动作）挂在一个专门的 `RemoteReplicator` 组件上。

4. 第四步是**把链路收口到可恢复的状态机**。场景切换期间，网络层可能继续收到位置/进入/离开等事件，需要在 `LoadSceneAsync` 期间做两件事：其一，**暂存**与该地图相关的网络消息（例如放入一个队列，在 `LevelLoadCompleted` 后统一重放），避免“边加载边实例化”造成丢对象或空引用；其二，对“重复进图”与“跨地图误消息”做防守（校验消息里的 `mapId` 必须等于当前目标地图，其他一律丢弃或延迟）。当 `LevelLoadCompleted` 触发后，你可以发一个“场景就绪/可见域就绪”的客户端事件，驱动：创建本地主角、刷新 UI、开始请求/处理 AOI 增量，最后把输入系统从禁用切回启用。

   > 最后是**若干必须补的细节**，否则线上容易炸：校验 `response.Characters` 是否非空再取下标 0，避免脏包导致越界；`DataManager.Instance.Maps` 要有健壮的查表与兜底（找不到资源名时给出可读错误并回退到上个界面）；在切换到新地图前清理旧场景里残留的网络实体、计时器和单例状态，防止幽灵对象；为 `LoadScene` 增加“加锁/防抖”标记，禁止多次并发加载同一场景；把 `User.Instance.CurrentCharacter` 的关键字段（地图 id、出生点）作为只读来源，真正的权威位置仍以服务器后续同步为准，客户端只做短时预测与插值。这样，客户端从“接到进图回包”到“完成场景切换与本地镜像初始化”的链路就闭合了：先落地自我身份，再解析目标地图并异步切换，加载完成时重放在途消息并生成世界镜像，随后进入正常的 AOI 同步与玩家操控循环。

### 角色显示在画面中

**1）入口在 MainCity 场景里的 `GameObjectManager`**
 场景加载完成后，`GameObjectManager.Start()` 立刻做两件事：

1. 一是 `StartCoroutine(InitGameObjects())` 启动**协程**，把当前 `CharacterManager` 里已经存在的所有角色逐一生成到场景（解决了**“场景一加载就要把已有实体刷出来”**的问题）；
2. 二是订阅 `CharacterManager.Instance.OnCharacterEnter` 事件，让后续任何“有新角色进入”的时刻，都能即时调用本地生成逻辑 `OnCharacterEnter → CreateCharacterObject`（解决了“动态进场”的问题）。脚本卸载时会把订阅清空，避免事件泄露。 

**2）角色/新增角色是怎样被“生成并摆到正确位置”的（`CreateCharacterObject`的逻辑）**
 `CreateCharacterObject(Character character)` 是生成单个角色的核心：

1. 它先用资源加载器 `Resloader.Load(character.Define.Resource)` 取出预制体，成功后 `Instantiate` 出游戏对象，并以“角色Id_名称”命名；
2. 随后用工具函数把**服务器下发的逻辑坐标**转换为**Unity 世界坐标**，分别设置物体的位置与朝向，
3. 最后把实例缓存到本地 `Characters` 字典，方便后续查找与去重。
4. 然后它为该对象上的 `EntityController`（驱动可视表现）与 `PlayerInputController`（本地输入控制）注入数据：若这是“自己”（`info.Id == CurrentCharacter.Id`），就把自己保存到 `User.Instance.CurrentCharacterObject`、把相机的跟随目标指向自己（`MainPlayerCamera.Instance.player = go`），并开启本地输入；若是别人，则禁用本地输入（只等网络驱动）。最后它调用 `UIWorldElementManager` 给角色挂上名字条。
5. 整个过程保证“看见谁、谁能被操作、谁只做镜像”三件事明确分流。 

**3）是谁在“触发”这些生成？——`CharacterManager`**
 `CharacterManager` 是一个客户端单例，内部维护 `Dictionary<int, Character> Characters` 保存所有已知角色的**客户端镜像**；当收到网络层（比如入图初始快照或 AOI 增量）新增一名角色时，`AddCharacter(NCharacterInfo cha)` 会把 `NCharacterInfo` 转为本地 `Character` 对象，放进字典，然后**触发 `OnCharacterEnter(character)` 事件**。由于 `GameObjectManager` 已经订阅了这个事件，它就会立刻走到上面的 `CreateCharacterObject`，把该角色实体实例化出来。移除时走 `RemoveCharacter`，把镜像从字典中删除（可配合销毁对应 `GameObject`）。这就是“数据到来 → 角色生成”的桥梁。 

**4）相机为何能一直跟随？——`MainPlayerCamera`**
 `MainPlayerCamera` 也是单例，暴露了一个 `public GameObject player;` 作为目标。`GameObjectManager` 在生成“自己”时把这个字段指向主角实例；随后 `MainPlayerCamera.LateUpdate()` 每帧把相机的 `transform.position/rotation` 对齐到 `player.transform`，所以画面就一直锁定在主角上。把跟随逻辑放在 `LateUpdate()` 的好处，是在本帧内**所有位移与动画**都完成后再更新相机，减少抖动与撕裂。 

**5）把整条链路拧成一句话**
 服务器下发入图或 AOI 推送 → `CharacterManager.AddCharacter` 产出/登记本地角色镜像并广播 `OnCharacterEnter` → `GameObjectManager`（场景入口）在初始协程里批量生成已有角色，同时持续监听 `OnCharacterEnter` 为新角色执行 `CreateCharacterObject`：加载预制体、用服务器坐标摆放、区分“自己/别人”赋控制器与相机 → `MainPlayerCamera` 每帧跟随 `player`，角色因此稳定呈现在画面中。整个设计把**数据管理（CharacterManager）**、**实例生成（GameObjectManager）**、**视角跟随（MainPlayerCamera）**三件事松耦合起来，既能在场景刚载入时补齐已有角色，也能在运行时为新进来的角色即时落地、上屏、可控。



## 补充

#### 1. 在服务端持久化 `T*` 实体的目的

- **“持久化”真正指的是：落库。**

  就是“玩家改了名字 / 升了级 / 坐标变了 / 装备了武器 → 我想让它别丢 → 写回 DB”。这个动作**最合适用的就是 `TCharacter` 这类 DB 实体**，因为它就是为 `DbContext.SaveChanges()` 准备的。

- **为什么要在服务端持久化？目的就两个：**
  1. **保证玩家数据不丢**（这是基础）
  2. **给“慢业务”一个统一入口**：比如 GM 修改、数据分析、离线奖励、补发道具，全都照着表结构搞；你服务端在线角色怎么设计都行，但落库必须是统一的、稳定的。

- 总而言之，**T 开头这批就是“存档格式”**。你游戏里想怎么玩、怎么组织逻辑、怎么同步、怎么做 AOI 都行，但最终你得把结果塞回这套存档格式里，这样下次上线还能还原。

#### 2. 三种Character对比

| 角色                                    | 面向谁                                  | 存在时间                  | 数据形态                                           | 典型字段                                   | 不能干的事                                                   |
| --------------------------------------- | --------------------------------------- | ------------------------- | -------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **TCharacter**                          | 数据库 / EF                             | 短（一次请求 / 一次加载） | **贴表结构**，int 为主，带导航属性                 | ID、TID、Name、MapID、MapPosX、Items(nav)  | 不能长久放在游戏世界里跑逻辑；不能跨线程乱用；不能直接发给客户端 |
| **Character**                           | 游戏服务器逻辑（地图、战斗、移动、AOI） | 长（角色在线期间）        | **面向游戏逻辑**，可以有 Vector3、枚举、组件、引用 | Position(Vector3)、State、当前地图、技能CD | 不能直接拿去 SaveChanges；不能直接发给客户端（字段太多/太敏感） |
| **NCharacter / NCharacterInfo** (proto) | 客户端 / 网络                           | 短（一次发送）            | **可序列化的传输结构**，字段裁剪过，类型受限       | Id、Name、Class、Level、MapId、PosX/Y/Z    | 不能直接拿来做业务判断；不能保存到 DB；不能挂运行时引用      |



## Q&A

#### 1. 你的项目里，玩家点击进入游戏到角色出现在场景里，这个过程你是怎么设计的？

这里核心要解决的问题是：客户端需要的数据太多，不能一次全给，也不能等所有数据都到了再加载场景。我把它拆成两个阶段：第一阶段先拿角色自身的数据，比如背包、装备、任务，这些拿到就可以初始化本地 **Manager**；第二阶段再拿地图数据，也就是这张地图里有哪些其他玩家和怪物，拿到这个才触发场景加载。这样做的好处是两件事并行——场景在后台异步加载的同时，实体数据也在准备，互不阻塞。

另外一个设计决策是，"触发场景加载"和"管理地图实体"我放在两个不同的 Service 里处理，`UserService` 只关心"我自己"，`MapService` 只关心"地图上有谁"，**职责分离**之后扩展起来也更清晰。

当时踩过一个坑：服务器会在两种情况下推送地图实体列表，一种是我自己进图的**全量包**，一种是别人进图时推给我的**增量包**。如果不加区分，别人进图就会错误地触发我的场景加载。所以我在处理这个消息时，会先在列表里找有没有"我自己"，找不到就说明这是别人的进图通知，直接跳过场景加载逻辑。

#### 2. 进入场景后，你是如何实现配置表的读取，将角色显示到画面中的？（`GameObjectManager.cs`中的`CreateCharacterObject()`）



#### 3. `GameObjectManager`中为什么要使用协程来`InitGameObjects`？

在 Unity 里把一大堆玩家对象**一次性创建出来会产生明显的“主线程卡顿”**。`GameObject.Instantiate`、添加组件、设置材质、加载贴图、运行 Awake/Start、以及第一次批量的动画/导航初始化，都是主线程开销——如果一次性做成上百、上千个对象，短时间内的 CPU 与 GC 峰值会把帧率拉成 1 帧/秒，用户体验极差。协程（`IEnumerator` + `yield return null`）的作用就是“把工作拆成小块，逐帧执行”，**把这些重任务切片到多帧里完成**，从而平滑化帧率，保证主循环可以继续渲染、处理输入和网络事件。你那段 `InitGameObjects` 每创建一个角色就 `yield return null`，等于是把“每帧只做一个角色创建”——明显减轻了瞬时负载。

另一方面，协程是 Unity 提供的**主线程友好异步工具**：**大多数 Unity API**（比如 Instantiate、transform 操作、组件访问）**必须在主线程调用**，不能放到后台线程去做。协程不像真正的线程那样并发执行，它仍在主线程，但允许你“暂停”函数，下一帧再继续，从而做到“**非阻塞的序列化工作”**。这对于 MMO 场景尤其合适：**可以先马上创建本地玩家（即时反馈），再用协程分帧加载附近玩家、NPC、装饰物，同时让 Loading UI 更新进度**，给玩家更好的感觉。

#### 4.
