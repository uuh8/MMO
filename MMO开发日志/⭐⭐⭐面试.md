## 1. 你简历上写了"基于 TCP + Protobuf 的双端通信"，能介绍一下你们这套网络层的整体设计思路吗？从客户端发出一个请求，到服务器处理完返回响应，中间经历了哪些步骤？

说到网络通信，首先要讲客户端和服务端共享的 Common 库，其中网络相关的核心有三个组件。

- 第一个是 **PackageHandler**，它解决的是 TCP 粘包问题。TCP 是字节流协议，本身没有消息边界，我们用 Length-Prefix 帧格式来重建边界：每条消息发出前在头部写入 4 字节的 body 长度，接收端先读 4 字节拿到长度 N，再等缓冲区里积累够 N 字节才取出来反序列化，不足就继续等。
- 第二个是 **MessageDistributer**，它是发布订阅调度器，内部维护一个以消息类型名为 Key、多播委托为 Value 的字典。各 Service 在初始化时调用 Subscribe 注册处理函数，消息到来后查字典触发对应委托，实现网络层和业务层的解耦。
- 第三个关键点是**线程模型**。Socket 的异步回调运行在 IO 线程，而 Unity 的所有 API 只能在主线程调用。所以 PackageHandler 解包后不直接执行业务逻辑，只是把消息 Enqueue 进队列，Unity 主线程在每帧的 Update 里调用 Distribute 统一消费——这是一个生产者消费者模型，保证所有业务代码都在主线程执行。

消息格式上，我们用一个顶层容器 NetMessage 包裹所有消息类型，内部 Request 和 Response 各持有所有子消息类型，发送时只填其中一个字段，接收端反序列化后检查哪个字段非 null 就知道是什么消息，类型识别由 Protobuf schema 本身承载，不需要额外的 type ID。

完整链路是：客户端 Service 层按照 proto 定义填充字段 → PackageHandler 序列化并加 4 字节长度头 → Socket 发出字节流 → 服务端 PackageHandler 按长度头拆包反序列化 → MessageDistributer 投递到对应 Service 的处理函数执行业务逻辑 → 构建 Response 走相同路径返回 → 客户端主线程 Distribute 触发订阅回调 → 更新 Manager 层数据 → 通知 UI 层刷新。





## 2. 客户端为什么逻辑层和表现层有100倍的差别？为什么要这么设计？

这个设计的核心原因是**浮点数在跨端环境下存在精度不一致**的问题。Unity 的 `Vector3` 用的是 `float`，也就是 **IEEE 754 单精度浮点数**，它本身就无法精确表示大多数小数。更危险的是，**每帧做位移积分的时候，float 的舍入行为在不同平台和不同编译优化级别下可能产生微小差异**，单帧看不出来，但累积几千帧之后，客户端推算的位置和服务端推算的位置就会出现肉眼可见的偏差，导致服务端的碰撞判定和客户端的表现对不上。

**所以逻辑层改用 `int32` 来存坐标**，整数运算在所有平台结果完全一致，从根本上消除了跨端累积误差。但 `int` 只能表示整数，**如果1个逻辑单位代表1米，那相邻两个合法位置之间就差了整整一米，`1.5米` 这样的坐标根本无法表示，角色移动就会非常粗糙**。所以需要一个缩放系数，让1个逻辑单位代表更小的物理距离，精度自然就上来了。

选100这个系数，是精度和地图范围之间的工程权衡。1个逻辑单位等于1厘米，`150` 就代表 `1.5米`，对MMO来说移动精度完全够用。同时 `int32` 最大值约2100万，换算下来地图范围上限是21万米，对一个MMO世界绰绰有余。如果系数选1000精度更高但地图上限压缩到2.1万米，选10的话精度又太粗，所以100是针对MMO场景下精度和范围之间最合适的平衡点。**表现层最后拿逻辑坐标除以100转回Unity浮点坐标，只是单位换算，不影响任何逻辑计算的正确性**。

## 3. 逻辑层和表现层之间是如何绑定和互相影响的？

Entity 和 GameObject 是完全分离的两层对象，Entity 是纯数据，GameObject 是纯表现，两者通过一套绑定机制关联在一起。

首先在时序上，Entity 比 GameObject 先存在。当服务端广播角色进入地图的消息时，客户端的 `CharacterManager` 会先**根据服务端数据创建 逻辑层Character 对象**，存入逻辑层的实体字典里，这个时候屏幕上什么都没有。

接着 `GameObjectManager` 收到角色进入的通知，根据 Character 里记录的资源路径，用 `Instantiate` 实例化对应的 Prefab，创建出 GameObject。这个 Prefab 上天生挂载了 `EntityController` 和 `PlayerInputController` 两个组件。

GameObject 创建完之后会做两件事完成绑定。

1. 第一件是**数据绑定**，把 Character 对象的引用注入到 `EntityController` 里，同时用 Character 当前的逻辑坐标换算成世界坐标，初始化 GameObject 的位置和朝向，让表现层的初始状态和逻辑层一致。
2. 第二件是**通知绑定**，`EntityController` 启动时把自己注册到 `EntityManager` 的通知字典里，后续只要这个 Entity 的数据发生变化，`EntityManager` 就会回调 `EntityController` 更新 Transform 和 Animator。

对于本地玩家还有一个额外处理，`PlayerInputController` 会被激活，键盘输入会修改 Character 的逻辑状态，这是唯一一个从表现层反向写入逻辑层的入口。其他玩家的 `PlayerInputController` 直接禁用，完全由服务端广播驱动。

所以整体关系是：**Character 是数据的真相，GameObject 是数据的投影，GameObjectManager 负责创建投影并建立绑定，之后逻辑层和表现层就通过这套回调机制保持同步**。 



## 4. 你说服务端收到客户端的移动同步请求之后，会广播给同地图所有在线玩家。那服务端是怎么知道"同地图有哪些玩家"的？服务端是如何管理这些实体的？

服务端也需要一套逻辑层来管理世界状态，这和客户端的 Entity 设计是同构的，只是服务端没有 Unity，纯粹是内存中的数据结构。

核心是 `EntityManager`，它维护两个数据结构：一个**全局的实体列表**，一个**以 mapId 为 Key 的分地图实体字典**。后者就是"知道同地图有哪些玩家"的答案。

实体的注册时机是玩家进入游戏时。`UserService` 收到 `GameEnterRequest`，把数据库里的角色存档转换成运行时 `Character` 对象，然后调用对应地图的 `CharacterEnter`，地图内部再调用 `EntityManager.AddEntity`，把这个角色按 mapId 分类存入字典，同时分配一个全局唯一的 entityId。

广播时，`MapService` 收到某个玩家的移动同步包，更新服务端权威状态后，从 `EntityManager.MapEntities[mapId]` 拿到该地图所有实体，遍历列表，对每个实体通过 `SessionManager` 用 characterId 查到对应的 `NetConnection`，再把同步数据发出去。`EntityManager` 解决"找到谁"，`SessionManager` 解决"怎么发给他"，两者配合完成广播。

玩家离开时，`EntityManager.RemoveEntity` 从两个数据结构里都移除，后续广播自然就不再包含这个玩家。



# <font color="#007c00">服务端网络部分</font>

## <font color="#921a1a">1. 服务端怎么区分不同客户端的请求？连接和角色之间是什么关系？（连接管理和会话设计）</font>

#### **运作流程**

服务端启动时，`NetService` 开始监听 TCP 端口。每当一个新客户端连上来，`NetService` 就为这条连接创建一个 `NetConnection` 对象，同时注册两个回调：收到数据时触发 `DataReceived`，断开时触发 `Disconnected`。从这一刻起，**这个 `NetConnection` 对象就是这条 TCP 连接的完整代理，服务端通过它来代表"某一个客户端"**。

`NetConnection` 上绑定了一个 `NetSession`，这是**业务状态容器**。刚连上来的时候 Session 是空的，账号和角色都是 null。玩家登录成功后，`Session.User` 被赋值为数据库里的账号对象；玩家选完角色进入游戏后，`Session.Character` 被赋值为运行时的角色对象。从此以后，服务端收到任何消息，都能通过 `sender.Session.Character` 直接知道是哪个角色发来的，消息体本身不需要携带身份信息，因为连接本身就是身份的载体。

#### **设计理念**

这是一个典型的"连接即上下文"设计。把身份状态绑定在连接上，而不是放在每条消息里，好处是消息体更小，服务端也不需要每次都去数据库验证身份，直接从内存里的 Session 取就行。连接和角色是一对一的关系，一条 TCP 连接在同一时刻只能操作一个角色。角色下线时 Session 里的角色引用被清空，连接断开时触发完整的角色离线流程。

#### **面试标准答案**

服务端对每一条 TCP 连接维护一个独立的连接对象，连接对象上绑定了一个 Session，Session 是这条连接的业务状态容器，记录了当前连接登录的账号和选择的角色。这样服务端收到任何消息，都能通过连接对象直接找到"是谁发来的"，不需要在消息体里携带身份信息，连接本身就是身份的载体。连接和角色是一对一绑定的，角色下线时 Session 里的角色引用清空，连接断开时触发角色离线流程，两条路径最终走同一套离线逻辑保证行为一致性。



### (1) `NetConnection`和 `NetSession`的关系是什么，为什么有了前者还需要维护一个后者？后者又是如何维护的(SessionManager)？

**为什么有了 NetConnection 还需要 NetSession？**

NetConnection 解决的是 **IO 层的问题**——怎么收字节、怎么发字节、连接断了怎么回调。它是一个纯粹的通信管道，本身对"这条连接背后是哪个玩家"完全无知。

但服务端处理业务的时候需要知道上下文：这条消息是谁发来的？他登录了哪个账号？选了哪个角色？这些信息跟 IO 没有任何关系，**硬塞进 NetConnection 会导致通信层和业务层耦合在一起**。所以把业务状态单独抽出来放进 NetSession，**NetConnection 只管收发，NetSession 只管"这条连接的业务档案"，职责分离**。

这也解释了为什么 `NetConnection` 用泛型 `NetConnection<T> where T : INetSession`——通信层甚至不知道 Session 里有什么，只知道它实现了 `INetSession` 接口（暴露一个 `GetResponse()` 方法），完全面向接口编程。

------

**NetSession 是如何被维护的？**

NetSession 的生命周期跟 NetConnection 完全绑定，一条连接创建时 Session 同时被 new 出来，连接断开时 Session 随之失效。Session 里的内容随着玩家操作逐步填充：

```
连接建立    → Session 创建，User=null, Character=null
登录成功    → Session.User = TUser（账号对象）
进入游戏    → Session.Character = Character（运行时角色对象）
断线/退出   → Session.Disconnected()，Character 清空，触发离线流程
```

------

**`SessionManager` 是做什么的？**

这里有一个关键问题：**NetSession 绑在 NetConnection 上，而 NetConnection 服务端没有一个地方集中存着所有连接的列表。当服务端需要主动找到某个玩家的连接（比如广播、私聊、服务端推送），怎么办？**

`SessionManager` 就是解决这个问题的。它维护一张 `Dictionary<characterId, NetConnection>`，本质是一个反向索引：

```
角色进入游戏 → SessionManager.AddSession(characterId, connection)
角色离线    → SessionManager.RemoveSession(characterId)
需要发包    → SessionManager.GetSession(characterId) → 拿到连接 → SendResponse()
```

注意 `SessionManager` 存的 Key 是 **characterId** 而不是 **userId**，因为**服务端的操作粒度是"角色"**，不是"账号"。

------

**面试标准答案**

`NetConnection` 和 `NetSession` 是职责分离的设计。

- **`NetConnection` 是纯粹的通信管道，负责字节流的收发和连接生命周期管理，对业务完全无知。**
- **`NetSession` 是业务状态容器，记录当前连接对应的账号和角色，服务端处理任何请求都能通过 Session 直接拿到上下文，消息体不需要携带身份信息。**

两者通过接口解耦，`NetConnection` 用泛型约束 Session 只需实现 GetResponse，通信层不依赖任何业务细节。

`SessionManager` 是一个全局的 `characterId` 到连接的反向索引，解决了「已知角色 ID，找到对应连接」的问题。玩家进入游戏时注册，离线时移除。广播、私聊等需要主动推送数据的场景都依赖这个索引，否则服务端无法在没有收到请求的情况下主动向特定玩家发包。

> <font color="#6d3acc">服务端的网络部分，我把它分成3层，第一层是最底层，也就是处理TCP字节流的层，这一层是在共享库中实现的，共享库中和网络相关的脚本有三个，一个用于处理字节流，也就是 **使用字节前缀来识别一个完整的报文，并设置一个64kb的字节缓冲，当缓冲区中已积累的字节数达到了完整报文所需的长度时，就取出并处理该报文 **，具体也就是使用`protobuf`的反序列化，将字节流反序列化成`NetMessage`类型，并通过反射获取到该`NetMessage`的字符串名称，用于第二个脚本文件，也就是分发器用于分发给该类`NetMessage`的响应函数，以此就达成了针对不同`NetMessage`的分发处理。</font>

### (2) 如何理解“面向接口编程”，`NetConnection`与`NetSession`两者通过接口解耦？

**`NetConnection` 的定义是 `NetConnection<T> where T : INetSession`，它只知道 T 是某个实现了 `INetSession` 接口的东西，而 `INetSession` 接口只暴露了一个方法：`GetResponse()`。**

`NetConnection` 在需要发包的时候，只调用 `session.GetResponse()` 拿到字节数据，然后通过 Socket 发出去。它不知道 Session 里有没有 Character，不知道有没有限频逻辑，不知道有没有 PostProcess——这些全是 `NetSession` 自己内部的事。

如果没有这层接口，`NetConnection` 就需要直接引用 `NetSession` 这个具体类，意味着通信层代码和业务层代码产生了直接依赖。以后换一套 Session 实现，或者给不同类型的连接用不同的 Session，就需要改动 `NetConnection` 的代码。

有了接口之后，`NetConnection` 只依赖 `INetSession` 这个抽象，任何实现了这个接口的类都可以插进来，通信层代码完全不需要改动。这就是"面向接口编程"——**依赖抽象而不是依赖具体实现**，就是解耦的含义。

### (3) 为什么要设计`NetConnection`和`NetSession`两个连接标识物？

先说清楚两者的包含关系：`NetConnection` 是**外层对象**，`NetSession` 是它内部的一个字段。也就是说拿到 `NetConnection`，通过 `connection.Session` 就能访问到 `NetSession`；但反过来拿到 `NetSession`，却无法反向找到 `NetConnection`。

为什么服务端要设置这两个对象？因为职责不同。**`NetConnection` 管的是 IO 层——持有 Socket、负责字节收发、处理连接断开，对业务完全无感知**。**`NetSession` 管的是业务层——记录登录的账号、选择的角色、待发送的响应缓冲区**。两者分离是为了让通信层和业务层互不依赖，`NetConnection` 通过 `INetSession` 接口访问 `Session`，甚至不知道 `Session` 内部有任何业务逻辑。

<font color="#6d3acc">明白了这个包含关系，`SessionManager` 存 `NetConnection` 而不是 `NetSession` 就很自然了。**服务端需要主动向某个玩家发包时，必须调用 `connection.SendResponse()`，这个能力在 `NetConnection` 上**。如果 `SessionManager` 只存 `NetSession`，你能读到角色数据，但没有 `Socket`，数据发不出去。而存 `NetConnection` 就等于同时拥有了发包能力和业务状态，一个对象解决两件事。所以 `SessionManager` 虽然名字叫 `Session`，本质是"通过 `characterId` 找到完整连接代理"的反向索引。</font>

## <font color="#921a1a">2. 服务端怎么控制发包频率？为什么要这么设计？</font>

#### **问题的根源：发包本身有成本**

每次调用 Socket.Send 都是一次**系统调用**。系统调用意味着 CPU 从**用户态切换到内核态**，内核处理完再切换回来，这个切换本身就有固定的时间开销，和发多少数据无关。也就是说发 1 字节和发 1000 字节的系统调用成本是一样的，但如果你发了 1000 次 1 字节，就产生了 1000 次切换开销。

MMO 服务端的特点是事件密集：一个玩家移动一次就要广播给同地图所有人，同时这帧可能还有聊天消息、状态变更、公会通知。如果每个事件都立刻单独发一次，系统调用频率会非常高。

------

#### **第一层解法：Response 累加器**

**解决思路是把"写数据"和"发数据"这两件事分开，中间加一个缓冲窗口。**

**<font color="#921a1a">`NetSession.Response` 不是"每次请求都 new 一个新对象"，而是一个持续存在的缓冲区</font>**。各个系统处理完业务逻辑后，只是把数据填进这个缓冲区，不会立刻触发发送。多个系统在同一时间窗口内各自往里填数据：移动同步填 `mapEntitySync`，聊天填 `chat`，状态变更填对应字段——大家往同一个 Response 对象里写，互不干扰，因为 Response 内部的每个字段对应不同的消息类型。最后只需要**一次打包和一次系统调用**就全部发出去。

------

#### **第二层解法：100ms 限频窗口**

调用 `SendResponse()` 时，内部先调 `GetResponse()`，`GetResponse()` 做的第一件事是判断：当前时间距上次真正发包是否超过100ms。没超过就返回 null，`SendResponse()` 拿到 null 直接返回，什么都不做，数据留在缓冲区继续等。超过100ms才真正打包发出，同时清空缓冲区，更新发包时间戳。

这意味着在这100ms窗口内，不管 `SendResponse()` 被调用了多少次，最终只会真正执行一次 Socket.Send，把这段时间内所有系统填进去的数据合成一个包发出去。

------

#### **第三层机制：PostProcess 后处理**

打包之前还有一个**后处理**步骤：调用 `PostResponser.PostProcess(Response)`。`Character` 实现了这个接口，在 PostProcess 里检查有没有聊天增量、公会通知、队伍状态变更等"被动推送"的数据，有的话就顺带塞进当前这次 Response。

这解决了一个实际问题：聊天系统本身不会主动触发 `SendResponse()`，它只能等别人触发发包的时候"搭便车"。PostProcess 就是这个搭便车的机制，保证了即使玩家只在移动没有任何交互，聊天消息也能通过移动同步包的 PostProcess 顺带发出去，不会被憋死。

------

#### **ForceFlush：限频的例外**

100ms 限频会让某些消息产生最多 100ms 的延迟。对于移动同步这类数据，100ms 完全可以接受。但对于登录响应、切图通知，客户端在阻塞等待，延迟 100ms 会让玩家感觉到明显卡顿。

所以设计了 `ForceFlush = true` 旁路：设置这个标记后，`GetResponse()` 直接跳过时间判断，立刻打包发出。发完之后标记自动清除，下一次发包重新走正常的限频逻辑。



### (1) 面试官：你说你项目中用到了“后处理”，你解释一下什么是后处理、为什么要用后处理、你项目中如何使用的后处理？

**什么是后处理**

后处理是在"数据已经准备好、但还没有打包发出"这个时间点插入的一个回调钩子。`NetSession.GetResponse()` 在真正打包之前，会调用一次 `PostResponser.PostProcess(Response)`，允许外部系统在这最后一刻往 Response 里追加数据，然后才统一打包发出。

**为什么要用后处理**

服务端有两类系统：**<font color="#007c00">主动类系统</font>**比如移动同步，每次处理请求都会触发发包；**<font color="#007c00">被动类系统</font>**比如聊天，它只产生数据，自己不知道什么时候该发出去。如果让被动系统自己触发发包，就破坏了合包设计，又回到高频小包的问题。后处理解决的就是这个矛盾——被动系统只管把数据准备好，不管发包；等主动系统触发发包的时候，通过这个钩子把被动系统的数据顺带带走，搭便车发出去。

根本原因是服务端有很多**<font color="#921a1a">"被动推送"类的系统</font>**——聊天、公会通知、队伍状态——**这些系统自己不会主动触发发包，它们只是产生了数据，等着被发出去**。但如果让这些系统各自调用 `SendResponse()` 主动发包，就违背了合包的设计，又回到了**高频小包**的问题。	后处理解决的就是这个矛盾：**<font color="#007c00">被动系统</font>**只负责把数据准备好，不管发包；真正发包由别的系统（比如移动同步）触发，触发时通过 PostProcess 钩子顺带把被动系统的数据一起带走。这样聊天消息就能搭移动同步包的便车发出去，不需要单独发一个包。

**项目中如何使用**

`IPostResponser` 是一个接口，只定义了一个方法 `PostProcess(NetMessageResponse)`。`Character` 类实现了这个接口，在玩家进入游戏时赋值给 `Session.PostResponser`。`Character.PostProcess` 里检查有没有聊天增量、其他需要顺带发送的数据，有就塞进 Response。

整条链路是：某个系统调用 `SendResponse()` → 内部调 `GetResponse()` → 限频通过 → 调 `PostResponser.PostProcess(Response)` → Character 把聊天等数据追加进去 → 统一打包发出。

`NetSession` 本身不知道 `Character` 的存在，它只依赖 `IPostResponser` 接口，这也是一次解耦——发包流程不和任何具体的业务类绑定，任何实现了接口的对象都可以作为后处理器挂进来。



### (2) 面试官：你说你的系统中有主动系统和被动系统，你细说一下这个部分

这里的主动和被动，指的是系统有没有能力决定"什么时候发包"。

**<font color="#007c00">主动系统是有请求-响应关系的系统。</font>**客户端发来一个请求，服务端处理完就发一个响应，**发包的时机是明确的——收到请求就是发包的触发点**。移动同步、登录、传送都属于这类，整个流程是由客户端的行为驱动的。

**<font color="#007c00">被动系统是服务端单方面产生数据的系统。</font>**以聊天为例，玩家A发了一条消息，服务端需要把这条消息推送给同地图的其他所有玩家。对于这些接收方来说，他们没有发任何请求，**服务端是主动推送的。这类系统自己没有发包的触发点，数据产生了但不知道什么时候发出去合适**。

如果让被动系统自己强行触发发包，就会产生一个独立的小包，破坏合包机制。所以被动系统的做法是：**把待发送的数据先写入缓冲区，然后等待。等到这条连接上的<font color="#6d3acc">下一次主动系统触发发包时</font>，后处理钩子被调用，被动系统在这个时机把缓冲区里的数据追加进当次包一起发出**。

本质上是一种"搭便车"的设计——被动系统不自己开车，等主动系统开车的时候坐上去。代价是被动数据可能会有最多一个合包窗口的延迟，但对于聊天、公会通知这类消息来说，100ms的延迟完全可以接受。



### (3) 面试官：你说的100ms延迟是什么意思？意思是客户端每秒只能接收10个包吗？这样客户端不会卡吗？

100ms 限频是<font color="#6d3acc">**服务端的发送限制**</font>，不是客户端的接收限制，这两件事不能混为一谈。

服务端每条连接最多每100ms发一次包，也就是每秒最多10个同步包到达客户端。但客户端的画面是60帧甚至120帧在跑，如果真的只靠每秒10个网络包来驱动角色移动，角色确实会每秒跳动10次，体验极差。

所以客户端有一套**<font color="#6d3acc">本地推算机制</font>**来填补这个空白。收到服务端的包之后，客户端记录下角色当前的位置、方向和速度，在两个包之间的**<font color="#6d3acc">每一帧都用"速度乘以时间"在本地做位移积分，让角色持续平滑移动</font>**。等下一个服务端包到来时，再用权威数据纠偏一次。

也就是说**<font color="#6d3acc">网络包解决的是"角色大方向正不正确"，本地积分解决的是"画面看起来流不流畅"</font>**，两者各司其职。每秒10个包对于状态同步的精度是够的，视觉上的流畅度由客户端本地计算保证，和网络包的频率无关。

所以100ms限频不会让客户端感觉卡，卡不卡取决于客户端有没有做好本地推算，而不是取决于网络包多不多。



## <font color="#921a1a">3. 服务端怎么把一个玩家的移动同步给同地图所有人？</font>

#### **运作流程**

每张地图内部维护了一个 `MapCharacters` 字典，Key 是 characterId，Value 是一个同时持有网络连接和角色对象的结构体。这个字典就是「同地图所有玩家」的完整索引。

当某个玩家发来移动同步包，`MapService.OnMapEntitySync` 收到后，先做三重校验（Session、Character、Map 是否都存在），然后调用 `Map.UpdateEntity`。`UpdateEntity` 遍历 `MapCharacters` 里的所有玩家，找到发包者就更新他在服务端的权威坐标，遇到其他人就调用 `SendEntityUpdate` 把这个移动数据推进对方的 Session 缓冲区。遍历结束后，每个在线玩家的缓冲区里都有了这次移动同步数据，等到各自的限频窗口到了就会发出。

#### **设计理念**

服务端的「广播」本质是 N 次单播，没有真正的组播。每条连接是独立的，服务端对每个玩家单独发送，数据内容相同但物理上完全分开。`MapCharacters` 字典同时持有连接和角色数据是一个关键设计决策——它避免了广播时再去另一个管理器里查连接，遍历一次字典就能同时完成「找到谁」和「怎么发给他」两件事。

这个设计的已知缺陷是广播复杂度是 O(N)，地图里玩家越多广播开销越大。生产级 MMO 会引入 AOI（Area of Interest，兴趣区域）优化：只把移动同步发给周围一定范围内的玩家，而不是地图里的所有人，把 N 压缩到一个常数范围。

#### **面试标准答案**

每张地图内部维护一个以 characterId 为 Key 的字典，同时存储网络连接和角色数据。收到移动同步包后，服务端遍历这个字典：找到发包者就更新其服务端权威坐标，遇到其他人就把同步数据推进对方的 Session 缓冲区。广播本质是 N 次单播，没有真正的组播。这个设计的缺陷是复杂度 O(N)，生产级方案会引入 AOI 兴趣区域管理，只同步给附近玩家，把广播范围从整张地图压缩到一个固定半径内。

## <font color="#921a1a">4. 服务端怎么处理并发请求？有没有线程安全问题？</font>

#### **运作流程**

服务端有三类线程并发运行。IO 线程负责接收字节流，`PackageHandler` 完成拆包后把消息 Enqueue 进消息队列，不做任何业务逻辑。`MessageDistributer` 启动了 8 个 Worker 线程并发从队列里 Dequeue，调用对应 Service 的处理函数执行业务逻辑。独立的主循环线程每 100ms 执行一次 `MapManager.Update`，推进刷怪、NPC AI 等世界状态。

#### **线程安全问题**

这里主动暴露两个已知缺陷。第一个：消息队列用的是普通 `Queue<T>`，IO 线程 Enqueue 和 Worker 线程 Dequeue 并发发生，`Queue<T>` 非线程安全，多线程并发读写存在竞态条件，生产环境应该替换为 `ConcurrentQueue<T>`。第二个：`Map.MapCharacters` 是普通 `Dictionary<T>`，多个 Worker 线程可能同时处理不同玩家发来的移动包，都在修改同一张地图的 MapCharacters，也存在竞态条件，应该替换为 `ConcurrentDictionary<T>` 或加 `ReaderWriterLockSlim`。

更根本的生产级解法是把所有游戏状态的修改收敛到主循环线程，Worker 线程只负责解析消息和入队，不直接修改游戏状态——这和 Unity 主线程模型的思路一致。

#### **面试标准答案**

服务端用 8 个 Worker 线程并发消费消息队列来提高吞吐量。但这里有两个已知的线程安全缺陷：消息队列用的是非线程安全的 `Queue<T>`，多线程并发读写存在竞态，应替换为 `ConcurrentQueue<T>`；地图内部的玩家字典也是非线程安全的普通字典，并发的移动同步请求会同时写同一张地图的数据，应替换为 `ConcurrentDictionary`。生产级的根本解法是把游戏状态修改收敛到单一主循环线程，Worker 线程只做消息解析和派发，彻底规避并发写的问题。

## <font color="#921a1a">5. 客户端突然断线，服务端怎么处理？</font>

#### **运作流程**

断线有两个入口。主动退出是客户端发 `UserGameLeaveRequest`，走 `OnGameLeave`。异常断线是 TCP 连接突然中断，Socket 接收到 `BytesTransferred=0` 或 `SocketError`，触发 `CloseConnection`，进而调用 `NetSession.Disconnected`。两条路径最终都汇聚到 `UserService.CharacterLeave` 这个统一入口。

`CharacterLeave` 按顺序执行四步：第一步从 `SessionManager` 里移除这条连接的索引，防止其他系统还往已断开的连接发包；第二步从 `CharacterManager` 里移除这个角色，防止其他逻辑还持有这个已离线对象的引用；第三步调用 `character.Clear()` 清空运行时状态，释放队伍、公会等引用，注意这一步必须在发送任何响应之前执行；第四步调用 `Map.CharacterLeave`，从地图的 `MapCharacters` 字典里移除，并遍历同地图所有在线玩家广播一条「有人离开」的通知。

#### **已知缺陷**

`Clear()` 在 `Map.CharacterLeave` 之前执行，但 `Map.CharacterLeave` 需要读取 `character.Info.mapId` 来定位地图。如果 `Clear()` 清空了 `mapId`，就会找不到地图，触发 `NullReferenceException`。这是一个执行顺序依赖的隐患，生产环境需要在 `Clear()` 之前先把 `mapId` 存到局部变量里。

#### **面试标准答案**

主动退出和异常断线走同一套离线流程，保证行为一致性。流程分四步：移除 Session 索引防止向死连接发包，移除全局角色注册防止悬空引用，清理运行时状态释放内存，最后从地图中移除并广播离开通知给同地图所有人。有一个已知的执行顺序 Bug：状态清理和地图离开的顺序存在 mapId 依赖，生产环境需要在清理前先暂存 mapId。整体设计原则是：异常流程不做特殊处理，复用正常退出的代码路径，减少遗漏和不一致的风险。
