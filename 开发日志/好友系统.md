## 流程

## 1）客户端 ↔ 服务端：好友系统整条逻辑链（按“消息怎么走”来梳理）

### A 发起添加好友（A → 服务器 → B）

客户端 UI 侧，玩家点“添加好友”，`UIFriends` 会弹输入框，把输入按“ID/名字”解析，然后直接调用 `FriendService.SendFriendAddRequest(friendId, friendName)` 发起请求；同时做了“不能加自己”的本地校验。

`SendFriendAddRequest` 会组装一个 `NetMessageRequest.friendAddReq`，把 `FromId/FromName` 填成自己，把 `ToId/ToName` 填成目标，然后发给服务器。
（协议里对应：`NetMessageRequest` 里 `friendAddReq=15`，`FriendAddRequest` 有 from/to 的 id/name。）

服务端 `FriendService.OnFriendAddRequest` 收到后，先定位发起者 `sender.Session.Character`，然后做两段校验/定位：如果 `ToId==0` 就在在线角色集合里按名字补齐 `ToId`；接着检查“是否已经是好友”，是的话直接回 `friendAddRes` 失败给 A；否则通过 `SessionManager.GetSession(ToId)` 找到 B 的连接（怪物不可能有 Session，所以用 Session 定位玩家最干净），找不到就回“好友不存在或离线”。

**校验通过后，服务端并不会替 B 做决定，而是把“加好友请求”原封不动塞进 B 的 Response**：`friend.Session.Response.friendAddReq = request; friend.SendResponse();`，这就是你协议里很特殊的一点——`FriendAddRequest` 同时存在于 `NetMessageResponse`（服务器用 response 通道推给 B）。

### B 弹窗选择接受/拒绝（B → 服务器）

B 客户端收到服务器推来的 `FriendAddRequest` 后，`FriendService.OnFriendAddRequest` 弹 MessageBox，让玩家点“接受/拒绝”，然后调用 `SendFriendAddResponse(true/false, request)` 把结果回给服务器。
这里的语义跟你的协议一致：`FriendAddResponse` 里面带 `result/errormsg/request`，其中 `request` 用来把当初那次 from/to 信息带回去（避免服务端还要维护一份“待处理请求上下文”）。

### 服务器落库 & 双向写入 & 通知双方（服务器 → A、B）

服务端 `OnFriendAddResponse` 收到 B 的结果后，会先把这份 response 写回 B 自己的 `Session.Response.friendAddRes`，保证 B 能收到处理结果。

如果 B 同意（`Result.Success`），服务端会通过 `SessionManager.GetSession(request.FromId)` 找到 A 是否还在线：A 下线则把 B 的结果改成失败“请求者已下线”；A 在线则执行真正的“建立关系”——双方各自 `FriendManager.AddFriend(对方Character)`，`DBService.Save()` 持久化，然后给 A 也发一份 `friendAddRes` 成功通知。

关键细节在 `FriendManager.AddFriend`：它会把新好友写入 `Owner.Data.Friends`（EF 持久化实体集合）并把 `friendChanged = true` 打脏标记。
这个脏标记会触发后面你说的“后处理”，从而把 `FriendListResponse`（好友列表）按需塞进即将发送的 response 里（下面第 2 部分会专门解释）。

### 删除好友（A → 服务器 →（可选）B）

客户端 UI 侧：选中列表项后点“删除好友”，二次确认后调用 `SendFriendRemoveRequest(关系Id, friendId)` 发给服务器。
（你协议截图里：`FriendRemoveRequest` 有 `id` 和 `friendId`，`id` 是这条好友关系记录的 id，`friendId` 是对方角色 id。）

服务端 `OnFriendRemove` 会：先删自己（按关系 id 删除 DB 记录并打 `friendChanged`），再尝试通过 `SessionManager.GetSession(friendId)` 看对方是否在线：在线就删对方内存里的“我”；不在线就直接删对方那条 DB 记录；最后 `DBService.Save()` 并回 `friendRemove` 响应给发起者。
这里有个非常现实的“工程坑”：你现在的代码只 `sender.SendResponse()`，并没有在对方在线时 `friend.SendResponse()`，所以**对方 UI 不一定立刻刷新**，可能要等它下次收到任何响应包时，才被后处理顺带把 friendList 推过去（这就是后处理的副作用：它让“什么时候推更新”变得隐式）。

### 好友列表怎么到 UI 上（FriendListResponse → UI 刷新）

客户端 `FriendService` 订阅了 `FriendListResponse`，收到后会把 `message.Friends` 写到 `FriendManager.Instance.allFriends`，然后触发 `OnFriendUpdate`，而 `UIFriends.Start()` 把这个事件绑定成 `RefreshUI()`，于是 UI 会清空并重建列表项。
列表项 `UIFriendItem.SetFriendInfo` 只是把 `NFriendInfo.friendInfo(Name/Class/Level)` 和 `Status` 映射到文本（在线/离线），选中态切换背景 sprite。

## 2）什么是“后处理 PostProcess”，为什么需要它，以及你这份代码的实现方式

### 概念：把“业务改状态”和“网络怎么打包发送”拆开

所谓后处理，本质是一个“发送前的统一整理步骤”：业务逻辑（比如加好友、删好友、扣钱）只负责把数据改对、把变化标记出来；真正发网络包之前，再由一个统一入口把“本次需要顺带发给客户端的增量数据”合并进 response。

你项目里用接口把这个机制固定成协议：`IPostResponser` 只定义了 `PostProcess(NetMessageResponse message)`，谁实现它，谁就能在发送前对 response 做最后加工。

### 为什么要后处理：减少包数量 + 减少全量重复 + 让“增量推送”可组合

不做后处理时，一个典型的糟糕情况是：

- “加好友成功”发一个 `FriendAddResponse`；
- “好友列表更新”再额外发一个 `FriendListResponse`；
- “金币/道具变化”再发一个 `StatusNotify`；
  最后客户端收到一堆碎片包，还得处理乱序/合并逻辑。

后处理的思路是：**只要你本来就要发一个 response（比如 friendAddRes / friendRemove / 任何业务响应），那我就尽可能把本次产生的增量（friendList、statusNotify）塞在同一个 response 里**。这样能显著减少网络包数量，也避免“每次都发整张好友表/整包状态”的浪费。

### 你的实现方式：Character 作为“聚合器”，把 FriendManager/StatusManager 的增量合并进 Response

你代码里，`Character` 实现了 `IPostResponser`，也就是“发送前整理器”的角色。
它在构造时就创建并持有 `FriendManager` 和 `StatusManager`，把它们绑定到角色身上（Owner = this）。

`Character.PostProcess` 做的事非常直接：先让 `FriendManager.PostProcess(message)` 去判断是否需要附带 `friendList`，再判断 `StatusManager.HasStatus`，有的话就 `StatusManager.PostProcess(message)` 把状态变化塞进 `statusNotify`。

- `FriendManager` 通过 `friendChanged` 脏标记控制是否需要生成 `FriendListResponse`：只有当 Add/Remove/UpdateFriendInfo 发生时才置 true，然后在 PostProcess 里重建 friends 列表并填充 `message.friendList`，最后清掉标记。
- `StatusManager` 则是把各种状态变化先攒在 `List<NStatus>` 里，发送前一次性写进 `message.statusNotify.Status`，然后清空，避免“每改一次就发一次”。

### “用 Session 找玩家而不是在 CharacterManager 里捞”的意义

你老师的那句判断其实是在防止架构走偏：当你把“玩家/怪物”都统一塞进某个管理器（比如 CharacterManager）时，业务层如果用“按 ID 在 CharacterManager 查”来定位网络对端，很容易在概念上混淆——**怪物是实体但不是连接，不存在 response 通道**。你服务端代码直接写明了：用 Session 的原因是“怪物和玩家共同管理，但只有玩家有 Session”。

------

### 顺手点两个你后面一定会遇到的“现实扩展点”（提前避坑）

后处理很好用，但它会让“更新推送的时机”隐式化：你在删好友里已经埋了一个例子——对方在线但没立刻 `SendResponse()`，那对方客户端什么时候刷新全靠“它下一次恰好收到某个响应包”。这在 MMO 里会被玩家当成 BUG。

比较稳的做法通常是：**后处理负责“打包合并”，但“该不该立刻推给谁”仍由业务逻辑明确触发**（比如删好友成功时，双方都要各自 SendResponse 一次，让后处理把 friendList 顺带塞进去就行）。这样你既保留“少发包”的收益，又不会把时序变成玄学。
