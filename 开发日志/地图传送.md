## 地图传送

实现流程：

#### 客户端

在客户端这边，每张地图场景（比如 `MainCity`）都会放一个空物体 `TeleportersMainCity` 作为容器，下面挂多个表示传送点的子物体。每个传送点只保留 `MeshFilter`，删除 `MeshRenderer`，再加上勾选了 `IsTrigger` 的 `BoxCollider`，形成实际的触发区域。传送点上挂 `TeleporterObject` 脚本，通过 `public int ID` 对应配置表里的 Teleporter ID。脚本在 `Start` 中用 `GetComponent<MeshFilter>().sharedMesh` 缓存好 mesh，然后在 `UNITY_EDITOR` 宏包裹的 `OnDrawGizmos` 里，利用 `Gizmos.DrawWireMesh` 和 `Handles.ArrowHandleCap` 在场景里画出线框和方向箭头，这些可视化代码只在编辑器存在，打包后被条件编译剔除。

运行时真正重要的是 `OnTriggerEnter`：当某个带 `Rigidbody` 的碰撞体进入传送点的触发区域时，用  `GetComponentInParent<PlayerInputController>()` 判断是不是玩家，如果不是直接 return；确认是玩家后，先用 `DataManager.Instance.Teleporters.TryGetValue(this.ID, out var td)` 安全地从 Teleporter 配表里取出当前这个“源传送门”的定义，取不到就报错并返回，避免空引用。拿到配置后，如果 `td.LinkTo > 0` 并且配表里存在对应的目标传送门，就调用 `MapService.Instance.SendMapTeleport(this.ID)` 把“我从哪个传送门出去”的 ID 发给服务器，由服务器决定具体传到哪儿，而不是直接在客户端决定目标地点。

#### 服务端

服务端在初始化 `MapService` 时订阅了 `MapTeleportRequest` 消息，当客户端调用 `SendMapTeleport` 时，会进入 `OnMapTeleport`。这个函数首先从会话里拿到当前角色，记录一条日志，然后检查 `request.teleporterId` 是否在 `DataManager.Instance.Teleporters` 中存在。如果源传送门 ID 不存在，直接写 warning 并返回；存在的话取出 `source`，继续检查它的 `LinkTo`：如果 `LinkTo == 0` 或者 Teleporters 里没有对应 ID，同样写 warning 并直接 return，避免再往下访问非法数据。在通过这些校验后，再从配表中拿到 `TeleporterDefine target = DataManager.Instance.Teleporters[source.LinkTo]` 作为目标传送点，将当前角色从 `source.MapID` 对应的地图中移除，随后把角色的 `Position` 和 `Direction` 更新为目标传送点的逻辑坐标，最后调用 `MapManager.Instance[target.MapID].CharacterEnter(sender, character)` 把角色加入目标地图。结合前面 MapTools 导出的坐标，这一步服务器就能把玩家精确地落在目标地图中的指定传送点位置，实现从“源传送门 ID → 配表 LinkTo → 目标传送门坐标”的完整链路。

```c#
// 角色离开原地图
MapManager.Instance[source.MapID].CharacterLeave(character);
// 角色进入新地图
character.Position = target.Position;
character.Direction = target.Direction;
MapManager.Instance[target.MapID].CharacterEnter(sender, character);
```

#### 补充——扩展配置表

为了让服务器知道每个传送门在地图上的准确落点位置，配置表扩展这一步由 Unity 编辑器工具来完成。`MapTools` 工具在菜单里挂了一个 `Export Teleporters` 命令，执行时先让 `DataManager` 把所有配表加载进来，然后遍历所有地图定义：**对每一张地图**，根据 `map.Value.Resource` 打开对应的场景，调用 `FindObjectsOfType<TeleporterObject>()` 找出场景内所有传送点。对每个传送点，先校验其 `ID` 在 `DataManager.Instance.Teleporters` 中是否存在，再校验 Teleporter 配表里的 `MapID` 是否和当前地图一致，保证配表和场景没有对不上的 ID 或 MapID。校验通过后，用 `GameObjectTool.WorldToLogicN(teleporter.transform.position)` 和 `WorldToLogicN(teleporter.transform.forward)` 把场景里的世界坐标、朝向转成逻辑坐标，写回对应的 `TeleporterDefine.Position` 和 `Direction`。所有地图处理完毕后，统一调用一次 `DataManager.Instance.SaveTeleporters()` 把更新后的 Teleporter 配表导出为 txt 配置文件，然后再切回原先编辑的场景。这样，服务端加载配置时，就能拿到由客户端关卡布置导出的、统一格式的传送点坐标和朝向。

#### 总结

整个流程合在一起，就是：

- 客户端只负责检测“玩家是否进入某个传送门”，并把**源传送门 ID** 发给服务器；具体传到哪张地图、落在哪个坐标、如何更新实体，都由服务器根据 Teleporter 配表中 `MapID + LinkTo + Position + Direction` 统一决定。
- 编辑器工具负责把关卡设计时摆放的传送点信息同步到配表中，保证服务端逻辑和客户端场景布局严格一致。这样既保证了地图传送的灵活性，也在架构上保持了“配置驱动 + 服务器权威”的 MMO 设计原则。
