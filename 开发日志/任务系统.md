### `ListView` 和 `TabView` 脚本

`ListView`做的事情：

- 管理一组 `ListViewItem`（AddItem / RemoveAll）。
- 维护“当前选中项 `SelectedItem`”。
- 当 `SelectedItem` 变化时对外发事件 `onItemSelected`。

`ListViewItem` 做的事情：

- 持有 `owner` 引用。
- 被点击时：
  - 把自己标记为 `Selected = true`；
  - 把 `owner.SelectedItem` 设为自己，驱动整个“取消旧选中→选中新项→触发回调”的链条。

> 点击底部按钮 → `TabButton.OnClick()` → `TabView.SelectTab` → `TabView.OnTabSelect` 事件 → `UIQuestSystem.OnSelectTab` → 改 `showAvailableList` → `RefreshUI()` → `ClearAllQuestList` + `InitAllQuestItems` → `ListView.AddItem` 建立 owner 关系

## 流程

### 客户端

玩家点一下 NPC，整条链路从这里开始运转。

首先是场景里的 `NpcController` 接到 Unity 的 `OnMouseDown` 回调，它会调用自己的 `Interactive()`。这个方法用一个 `inInteractive` 标记做节流，防止你连点 NPC 疯狂弹窗；如果当前没在交互中，就把标记设为 `true`，启动协程 `DoInteractice()`。在协程里，NPC 先执行 `FaceToPlayer()`，也就是慢慢转身朝向玩家，然后调用 `NPCManager.Instance.Interactive(npc)` 把“交互请求”交给 NPC 管理器处理，最后等待 3 秒把 `inInteractive` 重置，让下一次点击重新生效。

`NPCManager.Interactive` 相当于 NPC 行为分发中心。它接到一个 `NpcDefine`，先尝试执行任务相关逻辑 `DoTaskInteractive(npc)`，如果能处理任务就直接返回；如果没有任何任务相关内容、而且这个 NPC 的类型是功能型（比如商店、仓库），则走 `DoFunctionInteractive` 去触发事先注册的功能回调。在 `DoTaskInteractive` 里，会先问任务系统：**`QuestManager.Instance.GetQuestStatusByNpc(npc.ID)`，看这个 NPC 身上有没有跟当前角色有关的任务**。如果返回的是 `None`，说明这个 NPC 对你完全没任务，交互失败返回 `false`；如果不是 `None`，就调用 `QuestManager.OpenNpcQuest(npc.ID)` 打开这个 NPC 的任务对话。

`QuestManager.OpenNpcQuest` 做的是“从这个 NPC 身上挑一条最优先的任务出来”。它在 `npcQuests` 字典里找到这个 NPC 对应的三个列表：`Complete / Available / InComplete`，优先顺序是：先看有没有可提交的（Complete），没有再看可接的（Available），最后才看进行中的（InComplete），一旦找到就把那条 `Quest` 交给 `ShowQuestDialog`。`ShowQuestDialog` 决定要不要弹出 `UIQuestDialog`：如果这条任务还没接（`Info == null`）或者状态是 `Completed`，说明当前操作是“接任务”或“交任务”，就通过 `UIManager.Instance.Show<UIQuestDialog>()` 打开 UI，把 Quest 填进去，并把关闭事件绑定到 `OnQuestDialogClose`；如果任务是进行中但未完成，就不弹对话框，只是简单弹一条 `DialogIncomplete` 文本给玩家看。

当玩家在 `UIQuestDialog` 上点了“接受”或“提交”，窗口会以 `WindowResult.Yes` 关闭，触发 `QuestManager.OnQuestDialogClose`。这个回调把 `sender` 转回 `UIQuestDialog`，拿到里面的 `dlg.quest`：如果 `dlg.quest.Info == null`，说明是第一次接任务，于是调用 `QuestService.Instance.SendQuestAccept(dlg.quest)`；否则说明这条任务已经在身上，且此时 UI 能弹出代表它已经达到提交条件，就调用 `SendQuestSubmit(dlg.quest)`。`QuestService` 负责构造网络消息：创建 `NetMessage`，在 `Request.questAccept` 或 `Request.questSubmit` 里写入 `QuestId`，通过 `NetClient.Instance.SendMessage` 发给服务器；服务器处理完后回一个 `QuestAcceptResponse` 或 `QuestSubmitResponse`，`QuestService.OnQuestAccept / OnQuestSubmit` 收到响应，如果结果成功就回调 `QuestManager.OnQuestAccepted / OnQuestSubmited`。

最后一步，`QuestManager.OnQuestAccepted / OnQuestSubmited` 内部会调用 `RefreshQuestStatus` 用服务器下发的最新 `NQuestInfo` 更新本地任务状态：`allQuests` 更新或新增这条任务、重新计算可接任务、重建所有 NPC 的 `npcQuests` 三个列表，然后触发 `onQuestStatusChanged` 事件。每个场景里的 `NpcController` 在 `Start` 时都订阅了这个事件，所以一旦任务状态变化，它就会重新调用 `GetQuestStatusByNpc(npcID)`，再通过 `UIWorldElementManager` 更新头顶的任务图标（感叹号、问号、灰色标记之类）。这样从“点 NPC”到“弹任务对话框、发网络消息、更新任务状态、刷新 NPC 头顶标记”，整个交互闭环就完整走了一圈。

#### 简化版：

1. 玩家点击 NPC 时，首先进入 `NpcController.OnMouseDown`，它会触发 `Interactive()`，让 NPC 朝玩家转身并调用 `NPCManager.Interactive(npc)`。
   `NPCManager` 收到 NPC 后，优先执行任务交互逻辑 `DoTaskInteractive`：它向任务系统询问这个 NPC 当前对玩家是否有“可接、可交、进行中”的任务。
2. 如果 NPC 有任务，流程就交给 `QuestManager.OpenNpcQuest(npcID)`。
   这里会根据优先级（可交 > 可接 > 进行中），挑出一条最适合展示的任务，然后调用 `ShowQuestDialog(quest)` 打开任务对话窗口。
3. `ShowQuestDialog` 负责弹出 UI，并在关闭时回调到 ``。
   玩家如果在 UI 上点击了“接受”或“提交”，窗口关闭后会进入 `OnQuestDialogClose`，并调用 `QuestService.SendQuestAccept()` 或 `SendQuestSubmit()` 发网络消息给服务器。
4. 服务器处理完返回结果，`QuestService` 收到响应后调用 `QuestManager.OnQuestAccepted / OnQuestSubmited` 更新本地任务状态。
   `QuestManager` 刷新所有任务、重新计算 NPC 任务状态，并触发 `onQuestStatusChanged`，使场景中所有 NPC 的头顶任务图标即时更新。

整个闭环概括成一句话：

**点击 NPC → 判断任务 → 弹任务对话框 → 玩家接/交 → 发包 → 服务器返回 → 本地刷新任务 → NPC 图标更新。**



### 服务端

服务端这块，其实就是**“网关层的 QuestService + 角色内的 QuestManager + EF 数据表 TCharacter/TCharacterQuest”**三件事协同工作，把客户端那一套 UI 行为变成权威的数据读写和奖励结算。整体架构：客户端发 protobuf 消息到 GameServer，GameServer 通过 MessageDistributer 把不同类型的请求丢给对应的 Service，具体业务再落在每个 `Character` 自己的 Manager 上处理，然后通过 EF 把结果写回 SQL Server。

先看入口 `QuestService`。这个类在构造函数里向消息分发器注册了两个订阅：`QuestAcceptRequest` 和 `QuestSubmitRequest`，即客户端的“接任务”和“交任务”请求。代码是：`MessageDistributer.Instance.Subscribe<QuestAcceptRequest>(this.OnQuestAccept);` 和 `Subscribe<QuestSubmitRequest>(this.OnQuestSubmit);`，所以一旦网络层收到对应的请求包，就会调到这两个回调。`OnQuestAccept` 里先从连接中拿出当前角色 `Character character = sender.Session.Character;`，打一行日志，然后构建一份空的 `QuestAcceptResponse` 挂到 `sender.Session.Response.questAccept`，接着把真正的业务交给这个角色的 `QuestManager.AcceptQuest(sender, message.QuestId)`，方法返回一个 `Result`，最后把这个结果写进响应并调用 `sender.SendResponse()` 把回包推回客户端。`OnQuestSubmit` 完全同一个套路，只是换成了 `QuestSubmitRequest` 和 `QuestManager.SubmitQuest`。也就是说 **Service 自己基本不做业务判断，只负责“收到包→找到角色→把请求交给角色的 QuestManager→把结果装进 Response”。真正干活的是 `GameServer.Managers.QuestManager` 这个类，它是挂在 `Character` 上的一个 Manager。**

`QuestManager`构造函数接收 `Character owner`，保存成 `Owner` 字段，这样整个类里所有数据库访问都可以通过 `this.Owner.Data` 来操作。角色登录时，服务端要把身上的任务列表同步给客户端，就会调用 `GetQuestInfos(List<NQuestInfo> list)`：它遍历 `Owner.Data.Quests`，也就是 EF 导航属性 `TCharacter.Quests` 这张一对多的 TCharacterQuest 关系表，**把每一条 `TCharacterQuest` 转成一个网络层结构 `NQuestInfo` 加到列表里，等一会儿打包成 protobuf 回客户端**。转换逻辑在 `GetQuestInfo(TCharacterQuest quest)` 中实现：把数据库里的 `QuestID`、自增主键 `Id` 填成 `QuestId` 和 `QuestGuid`，把整型 `Status` 强转成枚举 `QuestStatus`，再把 `Target1/Target2/Target3` 三个字段打包成一个 `int[3]` 作为进度目标。这个地方相当于你在数据库世界（TCharacterQuest）和协议世界（NQuestInfo）之间建了一个“翻译器”，保证客户端和服务端看到的是同一条任务，只是表示方式不同。

**接任务**逻辑在 `AcceptQuest` 里。这个方法先拿当前连接对应的 `Character`，然后从服务器端的配置表 `DataManager.Instance.Quests` 中查找这个 `questId` 对应的 `QuestDefine`。如果查不到，说明客户端传了一个根本不存在的任务 ID，要么是包被篡改，要么就是客户端逻辑错误，于是直接在 Response 里写上 `"任务不存在"` 并返回 `Result.Failed`，实现了最基本的“服务器不信客户端”原则。**如果配置表里存在这条任务，才会真正去操作数据库：通过 `DBService.Instance.Entities.TCharacterQuests.Create()` 创建一条新的 `TCharacterQuest` 实体。**这一步区别于 `new TCharacterQuest()` 的地方在于：**`Create()` 会把对象挂到 EF 的上下文里，后面 `Save()` 时会自动插入数据库**。然后为这条记录填字段：`dbquest.QuestID = quest.ID;`，再根据配置表里的 `Target1` 是否为 `QuestTarget.None` 决定初始状态，如果任务没有任何目标，直接标记为 `Completed`，否则标记为 `InProgress`。紧接着，它调用 `GetQuestInfo(dbquest)` 把这条新任务转换成 `NQuestInfo`，挂到 `sender.Session.Response.questAccept.Quest` 中，这就是客户端用来刷新本地任务 UI 的那条数据。最后，把这条 `dbquest` 加入到 `character.Data.Quests`（也就是 EF 的导航集合），调用 `DBService.Instance.Save()` 落库，返回 `Result.Success`。这里有几个关键点：一是服务器永远以配置表为准校验 questId，二是任务状态的初始值完全由服务器根据 `QuestTarget` 决定，客户端不能随意指定。

交任务逻辑在 `SubmitQuest` 中。方法开头同样先取 `Character` 和配置表中的 `QuestDefine`，如果配置里都没这条任务，那就直接返回“任务不存在[3]”。如果配置存在，才在角色的任务集合里查对应的数据库记录：`TCharacterQuest dbquest = character.Data.Quests.Where(q => q.QuestID == questId).FirstOrDefault();`。如果查不到，说明这角色压根没接过这个任务，Response 写 `"任务不存在[2]"` 并失败返回。查到了之后，会先看当前状态是不是 `Completed`，如果不是，说明任务目标还没达成，直接返回 `"任务未完成"`。只有在 `Status == Completed` 的情况下，才会把状态改成 `Finished`，调用 `GetQuestInfo(dbquest)` 填进 `questSubmit.Quest`，并马上 `DBService.Instance.Save()` 一次，确保任务状态持久化。
紧接着是奖励结算部分：根据 `quest.RewardGold` 给角色加金币，根据 `RewardExp` 预留给经验系统处理（现在代码里被注释掉），再根据 `RewardItem1/2/3` 和对应数量调用 `character.ItemManager.AddItem` 给背包加物品。奖励都处理完之后再 Save 一次，这样金币和物品的变更也都被 EF 同步到数据库。最终返回 `Result.Success`，客户端收到成功回包后会通过自己的 `QuestManager.RefreshQuestStatus(info)` 更新本地状态并刷新 UI、NPC 头顶标记，这一块你客户端那边已经串过了。

从数据库关系图的角度看，这套任务系统是挂在 `TCharacter` 上的“一对多”扩展。`TCharacter` 表负责保存角色的基础信息：地图、坐标、职业、金币等，而 `TCharacterQuest` 则为每条任务单独记录一条：`Id` 为主键，`TCharacterID` 为外键指向角色，`QuestID` 对应配置表里的定义 ID，`Target1~3` 存三个进度数字，`Status` 存当前状态（InProgress/Completed/Finished）。

EF 帮你把这两张表通过导航属性关联起来，**`Character.Data.Quests` 就是对这个一对多关系的抽象；在逻辑层再包一层 `QuestManager`，负责把数据库实体转成协议对象，实施“接任务/交任务”的状态机变更和奖励发放，最外层再由 `QuestService` 把它和网络消息对接起来**。这样一圈下来，客户端点 NPC、点击“接受/完成”，最后在服务器端就会变成对 `TCharacterQuests` 的插入、更新以及对 `TCharacter` 金币/物品字段的修改，整个任务系统的权威状态都集中在数据库和 EF 上，客户端最多只是 UI 和输入层。
