## 流程

这套“读配置表”是**Excel→JSON(txt)→两端拷贝→按公共模型(\*Define.cs)反序列化→DataManager进程内缓存→各系统按ID查表**的流水线。客户端与服务端共用同一份数据契约（Common/Data 下的 `*Define.cs`），只是**读取介质**不同：服务端直接走磁盘，客户端既可走磁盘版 TextAsset，也可后续换成 Resources/Addressables。下面把全链路按时间顺序梳理清楚。

### 1) 产出阶段：Excel → JSON(txt)

- 你在 `Data/Tables` 维护 xlsx，执行 `Excel2Json.cmd` 把每张表导出为对应的 `*.txt`（内容是 JSON）。
- 导出的字段名、类型要与 Common 库里的 `MapDefine/CharacterDefine/TeleporterDefine/...` 完全一致（它们是强类型“数据契约”）。

### 2) 分发阶段：拷贝到运行目录

- **客户端**：拷贝到 `Client/Data`（最终需能被运行时代码读取到）。
- **服务端**：拷贝到 `Server/GameServer/bin/Debug/Data`（.NET 进程以该目录为工作目录，能直接 `File.ReadAllText`）。

### 3) 运行时装载（服务端）

- 服务器启动时调用 `DataManager.Instance.Load()`。
- `Load()` 逐个读文件、反序列化为**字典**缓存（以 ID 为键），如：
  - 读取地图定义并转成 `Dictionary<int, MapDefine>`，保存在 `Maps`，同理还有 `Characters`、`Teleporters`（以及后续可开的 `SpawnPoints/SpawnRules`）。这些都在你的服务端 `DataManager` 里清楚写着：从 `Data/MapDefine.txt`、`CharacterDefine.txt`、`TeleporterDefine.txt` 读取，再 `JsonConvert.DeserializeObject<Dictionary<int, ...>>(json)` 放入内存字典里，供各系统查询使用（地图加载、出生点、传送器、NPC 刷新等）。 

### 4) 运行时装载（客户端）

- 客户端侧 `DataManager` 也维护同名字典：`Maps / Characters / Teleporters / SpawnPoints`。
- 有两个入口：一个是同步的 `Load()`，一个是用于首屏 Loading 的**协程式** `LoadData()`，它分段读取三张表、每次 `yield return null` 让 UI 能显示进度，再将 JSON 反序列化到相同的字典结构里（与服务端一致，字段完全对齐）。 
- 你的客户端 `DataManager` 还提供了**编辑器保存**方法：把运行时对 `Teleporters/SpawnPoints` 的修改再序列化回 txt（便于关卡/工具迭代），对应 `SaveTeleporters()` 与 `SaveSpawnPoints()`。

### 5) 统一的数据契约（Common/Data/*Define.cs）

- 反序列化目标类型就是这些 `*Define`：例如 `MapDefine` 携带地图资源名、出生点、类型等；`CharacterDefine` 携带预制体路径、基础速度等；`TeleporterDefine` 携带传送器目标地图与坐标。
- **关键点**：客户端和服务端**都用这套类型**，所以你保证“一份 Excel → 两端一致的强类型对象”。这样游戏逻辑和美术资源的“查表”就对齐了。

### 6) 使用姿势（典型查询链）

- **客户端**：入图回包拿到 `mapId` → `DataManager.Maps[mapId].Resource` 得到 Unity 场景名，驱动 `SceneManager.LoadScene`；进入场景后，根据 `CharacterDefine` 找角色预制体路径，`Resloader/Resources.Load` 实例化；根据 `TeleporterDefine` 在 UI/触发器里做显示与交互。
- **服务端**：根据 `MapDefine` 初始化地图实例；根据 `SpawnPointDefine/SpawnRuleDefine` 建立刷怪器；根据 `TeleporterDefine` 校验切图逻辑；这些系统全部只依赖 `DataManager` 的只读字典，不直接碰文件。

### 7) 重要的工程注意事项

- **路径与工作目录**：服务端 `DataPath = "Data/"`，使用 `File.ReadAllText(DataPath + "MapDefine.txt")`，因此必须确保配置**位于进程工作目录**下（`bin/Debug/Data`），否则读不到。
- **异步/分帧加载**：客户端用 `LoadData()` 的 `yield return null` 分帧读取，避免首帧卡死。
- **扩展表**：`SpawnPointDefine/SpawnRules` 的读取目前在客户端被注释（将来开启时按同样模式读，建议读完立刻构建二级索引，如 `Dictionary<mapId, Dictionary<pointId, SpawnPointDefine>>`）。
- **版本一致性**：建议在每个 txt 首部加一个 `version` 字段，客户端/服务端启动时互相校验，避免“我加载了A版本地图、你跑着B版本刷怪”的错配。
- **构建自动化**：把“Excel→JSON→拷贝到运行目录”的步骤做成构建后事件/脚本，避免人工漏拷；服务端用 `CopyToOutputDirectory: Always` 也行。
- **资源解耦**：Unity 侧后续可把 `Resloader.Load<TextAsset>("Data/MapDefine")` 改为 Addressables/远程CDN，实现热更，但 `*Define` 类型与 `DataManager` 的使用层不变。

一句话把要点捏紧：**Excel 只是编辑器，txt(JSON) 是分发格式，`\*Define` 是两端共享的强类型契约，`DataManager` 是进程内只读数据库**——服务端用它驱动地图/刷怪/传送规则，客户端用它驱动场景加载/预制体实例化/交互显示；两端都通过同一反序列化路径把“静态配置”变成“可查询的字典”，这就是你的“读配置表”功能的完整闭环。

## **为什么客户端有 `Load` 和 `LoadData` 两个入口，而服务端只有一个 `Load`？**

1. 客户端有两种启动场景：

   - **阻塞式加载（`Load()`）**：在编辑器工具、测试脚本或无需过渡画面的地方，一次性把所有 txt/JSON 读入并反序列化到内存字典。简单、直接，但会**卡主线程**。

   - **非阻塞式加载（`LoadData()`）**：在游戏启动的“Loading 场景”里，需要**一边加载一边渲染 UI**（进度条、提示语、登录界面淡入等）。`LoadData()` 做成 `IEnumerator`，把“读取一张表→反序列化→建索引”拆成若干小步，每步之间 `yield` 一下，让 Unity 有机会绘制下一帧。

- 服务端没有渲染循环，不需要“每帧让出主线程”。它是**进程启动 → 同步读配置 → 完成后再开启网络服务**。因此一个同步的 `Load()` 就够了，反而更稳（启动流程清晰、容易排错）。

> `Load` 是“快但阻塞”的一次性加载，适合没有画面的场景；`LoadData` 是“平滑但略慢”的分帧加载，适合玩家可见的过场界面。把读取/反序列化的核心逻辑抽到公共函数里，`Load` 直跑、`LoadData` 分帧调度，既能保证启动体验顺滑，又不引入重复代码。
